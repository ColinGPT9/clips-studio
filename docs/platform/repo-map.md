## 1. What Clips Kitty is, in one paragraph

Clips Kitty (Clips Studio until 1.1.3, `README.md:31`) is a local-first AI clipping app for Windows: an Electron + React + TypeScript desktop shell in `ui/` that is only a client of a local Python FastAPI engine (`server/api.py:1-8`, `ARCHITECTURE.md:851-853`). The engine downloads a YouTube/Twitch/Kick video or imports a local file, transcribes it with faster-whisper, scores moments with a local Gemma model through Ollama (or a cloud provider on the user's own key), renders vertical clips with FFmpeg plus a YOLOv8 + TalkNet tracker, and can publish them (`core/pipeline.py:192-682`; `ARCHITECTURE.md`). One SQLite file holds videos, clips, jobs and settings blobs (`core/state.py`). One worker thread runs one job at a time (`server/jobs.py:3-6`). Everything reaches the engine over `http://127.0.0.1:8765` with no authentication (`server/api.py:583-589`). The app ships as a 6-7 GB frozen PyInstaller engine inside an Electron installer, via a GitHub web installer, the Microsoft Store and winget (`docs/RELEASING.md`; `docs/MSSTORE.md`; `packaging/winget/`). Licence AGPL-3.0 (`LICENSE`). App version 2.0.0 (`ui/package.json:3`), supported API version 1 (`server/api.py:34`).

### 3.2 The local API in numbers

- One `FastAPI` app built by `create_app(config, settings_path)` (`server/api.py:572`); every optional feature mounts onto it through a module-level `install(app, *, config, db, data_dir, …)` function (`server/api.py:629-706`). There are no `APIRouter`s (grep).
- **176 route decorators** on that app: `server/api.py` 86 (85 HTTP + `/ws`), `youtube_api` 20, `ai_api` 17, `uploadpost_api` 13, `woopsocial_api` 13, `automation` 13, `remote_render/service` 9, `integrations` 5 ([02 §0](repo-map/02-local-api-endpoints.md)); 153 distinct static paths ([03 §4](repo-map/03-local-api-probe.md)). `docs/API.md:11` says "86 HTTP endpoints", which counts only `server/api.py` and is stale.
- A **second, separate** FastAPI app exists: the remote-render gateway (`remote_render/gateway.py:50`), 10 `/v1/…` routes, HTTPS with a self-signed cert pinned by the worker at pairing, `X-Worker-Id` + `Authorization: Bearer <secret>` on every call, secrets stored hashed (`remote_render/gateway.py:56-62`, `remote_render/queue.py:112-145`, `remote_render/tls.py`). It is the only authenticated server in the repository.
- Auth on the local API: **none**. `TrustedHostMiddleware(allowed_hosts=["127.0.0.1","localhost"])` is a DNS-rebinding guard, CORS admits only the Vite dev origin (`server/api.py:577-589`; `docs/API.md:70-95`). Anything on the machine that can reach the port can read footage, delete clips, change settings and, if YouTube is connected, publish (`SECURITY.md`).
- Versioning: `API_VERSION = 1`, "Bumped only when a supported endpoint changes shape, never for additions" (`server/api.py:34`), returned by `GET /health` with `app_version` from `ui/package.json` (`server/api.py:711-716`, `server/feedback.py:260-297`). The FastAPI `version="0.1"` string (`server/api.py:576`) is unrelated and stale. `docs/API.md:127-142` draws the supported-vs-internal line: documented endpoints are supported and change only with a CHANGELOG note; "Everything else is internal: branding assets, creator memory, caption editing, the AI edit endpoints, feedback submission".
- Auto docs are on: `/docs`, `/redoc`, `/openapi.json` (`server/api.py:576`; `docs/API.md:60-67`).

## 4. Pipeline architecture

### 4.1 One entry point, flag predicates instead of a mode enum

- `process_video(url: str, config: dict, db: StateDB, force: bool = False) -> list[RenderedClip]` (`core/pipeline.py:192`) is the Shorts pipeline; callers are the queue worker (`server/jobs.py:270`), `_both_formats` (`server/jobs.py:667`), the CLI (`main.py:204`) and the channel daemon (`core/scheduler.py:97`).
- Longform has a second orchestrator, `process_longform(url, config, db, options)` (`longform/process.py:28-45`), that re-imports the Shorts stage functions (`_cached_or_download`, `_register_clip`, `_render_files`, …).
- "Modes" are booleans or dicts in `config["clips"]` read through predicates in `core/modes.py` (`is_vertical_live` :44, `is_gaming` :55, `gaming_scoring` :68, `sport` :82, `needs_framing` :159, `measures_reaction` :165). The worker copies the job payload onto those keys (`server/jobs.py:187-262`); the payload is built from the HTTP body by `_process_options` (`server/api.py:440-550`), which also enforces mutual exclusion with HTTP 400 (`server/api.py:533-550`).
- Stages in order, each marked by a DB status and a progress event rather than a returned object (`core/pipeline.py:192-682`): download (`:205-250`, `downloaded` at `:304`) → creator memory and hype/chat prefetch threads (`:252-296`, `:343-362`) → transcribe (`:390-420`, `transcribed`) → signals + optional prepasses joined with `cancel.wait` (`:427-430`) → `find_clips` (`:439-451`, `analyzed` at `:463`) → metadata (`:514-519`) → render in `parallel_renders` worker threads or on remote workers (`:583-658`) → `_register_clip` per clip (`:1563`) → `done` (`:673`).

### 4.2 The data that crosses stage boundaries

`core/models.py`: `DownloadedVideo{video_id, title, path, duration, channel, games, description}` (`:11-25`), `Segment{start, end, text, words}` (`:28-40`), `ClipCandidate{start, end, score, hook, reason, source, engagement, trending, subscores}` (`:43-74`), `Rejection` (`:77-83`), `RenderedClip{source_video_id, candidate, path}` (`:86-92`); `analysis/metadata.py:60-67 ClipMetadata{title, description, hashtags, headline, subline}`. Files: `data/downloads/<video_id>.mp4`, `data/transcripts/<video_id>.json` (`{"video_id","language","segments":[…]}`, `transcription/transcriber.py:249-257`), `data/clips/<channel>/<title> [<video_id>]/clip_SSSSS-EEEEE.mp4` (`core/pipeline.py:498-503`, `:1151-1152`), `data/logs/job_<id>.log` (`server/jobs.py:150`). The repo's own rule: "Stages communicate only through dataclasses and files" (`ARCHITECTURE.md:1001`).

### 4.3 Detection is separate from rendering, and the DB funnel accepts any file

- Detection ends at `find_clips(video_path, segments, llm, config, signals=, creator_context=, weight_bias=, audience=, measure_reaction=, gaming=, chat=, sounds=, intent=, sport=) -> (list[ClipCandidate], list[Rejection])` (`analysis/fusion.py:54-70`), one function for every mode.
- Rendering is `_render_files(source, candidate, segments, clip_dir, config, render_opts=None, content_language="en") -> (Path, render_opts_json)` (`core/pipeline.py:1123-1138`): "Pure file work … NO database access and NO LLM call, so it is safe to run in a worker thread". It is already called from four other places: `server/api.py:1732` (preview), `server/jobs.py:686` (re-render), `remote_render/worker.py:366` (remote worker), `longform/process.py:35-44`.
- Registration is `_register_clip(db, video_id, candidate, final_path, meta, render_opts_json, config)` (`core/pipeline.py:1563-1581`), "the one place every finished video passes through". Nothing checks that `final_path` came from `_render_files`; `_sport_reels` (`:685-754`) and longform `_highlights` (`longform/process.py:277-296`) register files they made themselves with synthetic candidates.
- The remote-render dispatcher is already a renderer-replacement interface: `render_all(video_id, source, items, segments, clip_dir, config, render_opts, language, workers, …)` yields `(candidate, meta, get_result)` with `get_result() -> (clip_path, render_opts_json)` (`remote_render/dispatch.py:90-100`), consumed at `core/pipeline.py:654-657` and `longform/process.py:192-196`. A remote job is data, never a command: a keyframe-cut piece, the candidate, nearby segments, `render_opts`, and an allow-listed config slice `CONFIG_SECTIONS = ("clips","tracking","video")` (`remote_render/protocol.py:15-33`, `remote_render/piece.py`).
- What is **not** separated: `process_video` is one ~490-line function; download and transcribe cannot be replaced without editing it (`core/pipeline.py:192-682`). `render_opts` is an untyped dict of ~20 keys documented in comments (`core/pipeline.py:1136-1139`, `:1456-1482`; key table in [10 §2](repo-map/10-video-ffmpeg-render.md)).

### 4.4 Jobs, queue, progress, cancel, errors

- Jobs table: `type` ∈ `process|render|translate` (anything else raises `ValueError("Unknown job type …")`, `server/jobs.py:287`), `status` ∈ `queued|running|done|failed|cancelled`, `payload` JSON, `log_path`, `attempts` (`core/state.py:62-70`, `:412-437`). One `Worker(threading.Thread)` claims jobs in order (`server/jobs.py:49-340`); render and translate jobs go ahead of waiting process jobs (`core/state.py:1275-1305`). The queue **starts paused** (`core/queue.py:59-66`) and is capped at `MAX_ACTIVE = 5` (`core/queue.py`; `docs/API.md:443-449`).
- Progress: `core.progress.emit(**event)` to a single process-wide handler (`core/progress.py:18-39`); the worker stamps `job_id` and publishes `{"type":"progress", …}` (`server/jobs.py:109-123`); `server/events.py Broadcaster` fans out to `/ws` clients with a 200-event queue that drops when full (`server/events.py:25-30`). Stage names are a closed set with weights in `server/jobs.py:37-46 _STAGES`, mirrored by hand in `ui/src/renderer/src/lib/jobProgress.ts:17-28`. Event `type`s: `queue`, `job`, `progress`, `model_pull`, `publish`, `automation` ([02 §6.2](repo-map/02-local-api-endpoints.md)). Gaming and Sports code emits no progress at all; prepasses are `print()` only (grep; `core/pipeline.py:372-384`, `:898-914`).
- Cancel: cooperative, `core/cancel.py` (`request_cancel` :36, `check(video_id)` :46, `check_active()` :52, `wait(thread, timeout)` :80, `run(cmd)` :99 for FFmpeg, `CancelledError` :32); `POST /cancel` (`server/api.py:1201`).
- Errors: `find_clips` exceptions fail the job with a scrubbed traceback (`server/jobs.py:292-310`); per-clip render failures are caught and folded (`core/pipeline.py:616-626`); every call into `gaming/` and most into `sports/` is wrapped so a failure degrades to the standard path (`core/pipeline.py:803-829`, `:896-914`, `:1550-1560`; the rule is stated in `gaming/run.py:66-67` and `ARCHITECTURE.md:1012-1014`). Unguarded sport hooks: `check_titles` (`core/pipeline.py:523-528`) and the fusion sport branch (`analysis/fusion.py:276-285`).
- Logging: no `logging` module anywhere in the engine; ~300 `print()` calls captured by a `_Tee` into a 400-line ring and the per-job log file (`server/feedback.py:31-104`); stdout is discarded by Electron in packaged builds (`ui/src/main/index.ts startBackend`). Secrets are scrubbed on the way out (`core/scrub.py`, `server/feedback.py:135 redact`).

Detail: [05](repo-map/05-pipeline-core.md), [06 §1.4-1.6](repo-map/06-shared-pipeline-interface.md).

## 5. Gaming and Sports side by side: the interface they already share

## 8. FFmpeg and rendering

- FFmpeg/ffprobe location is one function: `core/binaries._resolve` (`:58-82`): `CLIPS_STUDIO_FFMPEG` env → beside the exe → `vendor/ffmpeg` → PATH. `tests/test_binaries.py:148-170` enforces that every subprocess goes through it.

## 11. Packaging, distribution and updates, and what they imply

- Build: `scripts/build_installer.py` on a Windows machine (~2.5 h, ~30 GB, CUDA torch required, not in CI): fetch scripts → PyInstaller one-dir console app `backend/api.exe` + `_internal/` → `npm run build` → electron-builder NSIS web installer + zip (`docs/RELEASING.md`; `clips-studio.spec`; `ui/electron-builder.yml`). The spec bundles `config/`, prompts, the two yaml knowledge files, outro MP4s, weights, FFmpeg, Ollama and Whisper, and lists hidden imports for every lazily imported module, including `collect_submodules("sports")` (`clips-studio.spec:51-53`, guarded by `tests/test_packaging.py`).
- Channels: GitHub web installer whose 5.9 GiB payload lives on a Hugging Face model repo because release assets cap at 2 GiB; Microsoft Store MSIX (Store ID `9NB6XT7DSQZZ`, Microsoft re-signs, updater disabled); winget pointing at the installer; a contributor Docker image (`docs/RELEASING.md`; `docs/MSSTORE.md`; `packaging/winget/`; `Dockerfile`).
- Updates: `electron-updater` generic feed (`latest.yml` with SHA512), manual download and "Restart & install", never automatic (`ui/src/main/updater.ts`). Every release is a wholesale replacement of one monolithic payload; there is no component feed and no in-app download of code. The only runtime downloads are Ollama models and Piper voices ([01 §10.1](repo-map/01-structure-config-packaging.md)).
- Consequences for third-party code: the frozen engine has no `pip` and cannot run `-m` (`requirements.txt` Piper comment; `server/mcp.py:10-16`), so a Python plugin can import only what the bundle contains and anything imported lazily needs a `hiddenimports` line at build time; the install directory is read-only under MSIX, so plugin files must live under the per-user data dir (`core/paths.py:95-100`); release cadence is slow and manual, so a registry needs its own update path (inferred). Existing out-of-process precedents: the render worker child with a JSON job and an allow-listed config slice (`remote_render/worker.py:82-87`, `remote_render/protocol.py:16-27`), and the MCP server and OBS plugin driving the engine purely over HTTP.
- Dependency policy: floors and major ceilings in `requirements.txt`, licence in `NOTICE`, spec entry, rebuild, sandbox test ([01 §11.1](repo-map/01-structure-config-packaging.md)); CI installs only `pyyaml ruff pytest requests` (`.github/workflows/ci.yml`), so any test importing numpy, cv2, fastapi or yt-dlp must `pytest.importorskip` ([12 §3](repo-map/12-extension-seams-conventions.md)).

## 15. How would an outside process run a pipeline through the existing API today, and what is missing?

Today an outside process on the same machine, with no credentials, can **drive** the pipeline end to end and nothing more. It calls `GET /health` and checks `api_version == 1` (`server/api.py:711-716`), then `GET /health/preflight` and refuses to start on any failing `blocking` check (`:718`); it submits `POST /jobs {"url": …, options}` for a YouTube/Twitch/Kick link or `POST /videos/local {"path": …}` for a file already on disk (`:803`, `:867`), reading `job_id` (which may be `null` with `already_processed`/`already_queued`) and optionally passing `webhook_url`/`webhook_secret` or a `then` action; it must `POST /queue/resume` because the queue starts paused and nothing starts on its own (`core/queue.py:59-66`; only `/integrations/streams` auto-starts, and only when alone, `server/integrations.py:150-153`); it waits by listening on `ws://127.0.0.1:8765/ws` for `{"type":"progress","job_id":N,…}` and `{"type":"job","job_id":N,"status":"done|failed|cancelled",…}` (`server/jobs.py:121`, `:361-383`), by receiving the one signed `job.done` POST (`server/webhooks.py:104-145`), or by polling `GET /jobs/{id}` (`:985`); then it reads `GET /videos/{video_id}/clips` for ranges, scores, titles, hashtags and local paths (`:1470`), `GET /media/{clip_id}` for the bytes (`:2001`), `GET /clips/{id}/captions|words` for text (`:1545`, `:1981`), copies files out with `POST /clips/{id}/export` or `/export/batch` (`:2243`, `:2247`), optionally re-cuts with `POST /clips/{id}/render` (`:1679`), and publishes through `POST /publish/plan` → `/publish/plan/execute` or `/woopsocial/batch/plan` → `/woopsocial/batch`. `examples/drive_the_api.py:42-167` is exactly this sequence and `main.py mcp` wraps it as tools. What it **cannot** do is extend the pipeline: it cannot register a pipeline, stage, scorer, source, layout, job type or preset (every mode is a fixed field in `JobIn` mapped onto `cfg["clips"]` in `Worker.run` and dispatched to three hard-coded entry points, `server/jobs.py:187-287`; `PRESETS` is a literal, `server/integrations.py:34`); it cannot get the downloaded source file or the transcript as data (no `GET /videos/{id}/source` or `/transcript`; the files sit at `data/downloads/<id>.mp4` and `data/transcripts/<id>.json`, `server/api.py:1716`, `:1290-1291`); it cannot hand back its own candidates or finished clips (clip rows are created only by `_register_clip` inside the pipeline, `core/pipeline.py:1563`); it cannot report progress into the job's bar or log (`core.progress.emit` is in-process, `core/progress.py:30`; `/ws` is one-way, `server/api.py:1428-1440`; the only inbound progress route belongs to the authenticated render gateway, `remote_render/gateway.py:122`); it cannot run transcription, scoring or a render of an arbitrary range on its own (no such endpoints; `/clips/{id}/render` needs an existing clip row); it cannot authenticate or be scoped, so any plugin has the whole API including `DELETE /videos/{id}` and `PATCH /settings` (`server/api.py:583-589`); and it inherits one worker, one job at a time (`server/jobs.py:3-6`), a queue cap of 5 and a one-attempt 10 s webhook. The nearest existing seams for a plugin SDK are, on the Python side, the scoring-profile duck type and the guarded hook surface Gaming and Sports already share (§5), `_render_files` for DB-free rendering, `_register_clip` as the funnel that accepts any finished file, and `render_all`'s generator as a renderer-replacement interface; on the process side, the `install(app, …)` module pattern, `queue.enqueue_once` + `start_if_alone`, the authenticated remote-render worker protocol, and the MCP tool list as an already-curated safe surface over the HTTP API.
