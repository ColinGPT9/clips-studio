# ComfyUI — research notes

- Platform: ComfyUI (ComfyUI core + ComfyUI-Manager + Comfy Registry)
- Tier: Track A, Tier 1 (thorough, including source)
- Date read: 2026-10-06 (every URL below was opened on this date unless marked otherwise)
- Brief's question: how does an AI application become an ecosystem of community-built extensions?
- Verdict (two lines): ComfyUI became an ecosystem by making the extension unit nearly free (a folder under `custom_nodes/` whose `__init__.py` exports `NODE_CLASS_MAPPINGS`, imported in-process at startup, with no manifest required) and by shipping a community-maintained Manager with a static Git index; it then spent 2024-2026 retrofitting the trust layer it never had: a central registry with immutable semver versions and a scanner, a "verified" check that in code means "not flagged", loopback-only gating of risky installs, and standards banning `eval`/`exec`, runtime `pip install` and obfuscation after three real supply-chain incidents.
  Clips Kitty should copy the low floor (one folder, one `pyproject.toml`-style manifest, one entry point), the version and status discipline of the registry, and the snapshot/rollback and "install what this file needs" conveniences, but not the in-process, shared-Python-environment execution model and not the install-time scripts that made the retrofit necessary.

Source conventions: "core" = shallow clone of https://github.com/comfyanonymous/ComfyUI at commit d49e8885 (committed 2026-10-06, `comfyui_version.py` = 0.39.0); "Manager main" = shallow clone of https://github.com/Comfy-Org/ComfyUI-Manager `main` at commit 855a0f50 (2026-10-03, pyproject version 3.42); "Manager 4.3" = the PyPI sdist `comfyui_manager-4.3.tar.gz` (read only, not executed), which is the packaging ComfyUI core pins (`manager_requirements.txt` = `comfyui_manager==4.2.2`); "frontend" = shallow clone of https://github.com/Comfy-Org/ComfyUI_frontend at commit b4f55185 (2026-10-06). Inferences are marked "(inferred)".

## 1. The unit of extension

- The unit is a **custom node pack** ("node pack", "custom node"): a Python module directory (or a single `.py` file) placed in `ComfyUI/custom_nodes/`. Core scans every entry of every `custom_nodes` path at startup and imports it; a module counts if it exports `NODE_CLASS_MAPPINGS` (V1 schema) or a callable `comfy_entrypoint` returning a `ComfyExtension` (V3 schema). Modules whose names end in `.disabled` are skipped. (core `nodes.py`, `load_custom_node` and `init_external_custom_nodes`; https://docs.comfy.org/custom-nodes/backend/lifecycle.md)
- One pack can add many nodes. Each node is a class with `INPUT_TYPES`, `RETURN_TYPES`, `FUNCTION`, `CATEGORY` (V1) or a `ComfyNode` with `GET_SCHEMA()` (V3). Node names "must be unique across the Comfy install" (lifecycle doc). Core node names cannot be overridden by a pack (`load_custom_node(..., ignore=base_node_names)`), but two packs can define the same node name; the later import wins (`NODE_CLASS_MAPPINGS[name] = node_cls`). Manager shows these as "Conflicted Nodes" and the legacy index has a `preemptions` field to declare which pack wins. (core `nodes.py`; Manager main README; `custom-node-list.json` entry for ComfyUI Impact Pack has `"preemptions": ["SAMLoader"]`)
- Four categories of pack: server-side only (Python), client-side only (JavaScript served from `WEB_DIRECTORY`, only `.js` files are served), independent client+server, connected client+server ("Any node that requires Client-Server communication will not be compatible with use through the API"). (https://docs.comfy.org/custom-nodes/overview.md)
- Other shareable units ride on packs: example workflows (`example_workflows/*.json` + thumbnails, served through `/api/workflow_templates`), subgraph blueprints, node help pages, i18n files. (https://docs.comfy.org/custom-nodes/workflow_templates.md; https://docs.comfy.org/custom-nodes/intro.md)
- Scale: Comfy Org's own April 2026 post claims "60,000+ nodes built by contributors" and "4 million users" (vendor blog, market fact: https://blog.comfy.org/p/comfyui-raises-30m-to-scale-open).

## 2. Manifest or metadata format

File: `pyproject.toml` in the pack root. It is required for publishing to the registry; it is **not** required for loading. `comfy_config/config_parser.py` in core creates a default config from the folder name when the file is missing, so an un-manifested folder still loads (core `comfy_config/config_parser.py`, `extract_node_configuration`).

Real field names (https://docs.comfy.org/registry/specifications.md; https://docs.comfy.org/registry/publishing.md; core `comfy_config/types.py`):

| Section | Field | Required | Notes |
| - | - | - | - |
| `[project]` | `name` | yes | The node id; "Immutable after creation"; < 100 chars; alphanumerics, `-`, `_`, `.`; case-insensitive; used in `comfy node install <node-id>` and registry URLs |
| `[project]` | `version` | yes | Semantic versioning X.Y.Z |
| `[project]` | `description`, `license` (`{file=}` or `{text=}`), `requires-python`, `classifiers` | recommended | Classifiers carry OS (`Operating System :: Microsoft :: Windows` ...) and accelerator (`Environment :: GPU :: NVIDIA CUDA` ...) support; core validates against a fixed allow-list |
| `[project]` | `dependencies` | optional | pip requirement strings; the docs show `dynamic = ["dependencies"]` + `[tool.setuptools.dynamic] dependencies = {file = ["requirements.txt"]}`; a `comfyui-frontend-package>=x,<y` entry declares frontend compatibility |
| `[project.urls]` | `Repository` | yes | GitHub URL; also `Documentation`, `"Bug Tracker"` |
| `[tool.comfy]` | `PublisherId` | yes | Globally unique, immutable, "typically matching your GitHub username" |
| `[tool.comfy]` | `DisplayName`, `Icon` (<= 400x400), `Banner` (21:9) | optional | |
| `[tool.comfy]` | `requires-comfyui` | optional | Version range of ComfyUI core, operators `<`, `>`, `<=`, `>=`, `~=`, `!=`, ranges |
| `[tool.comfy]` | `includes` | optional | Force-include git-ignored folders (e.g. `['dist']`) in the published archive |
| `[tool.comfy]` | `web`, `Models` (list of `{location, model_url}`) | undocumented | Present in core `comfy_config/types.py` (`ComfyConfig.web`, `ComfyConfig.models`); `web` is used by core to auto-register the JS folder; `Models` is not described in the specifications page and comfy-cli's custom-node command does not reference it (grep of `comfy_cli/command/custom_nodes/command.py`) |

Other files with meaning (Manager main README "Custom node support guide"): `requirements.txt` ("will be installed automatically"), `install.py` ("automatically called"), `uninstall.py`, `node_list.json` (manual node list when the mapping pattern is unconventional), `.comfyignore` (gitignore syntax; excludes git-tracked files from the published archive), `prestartup_script.py` (executed by core before the server starts; core `main.py` `execute_prestartup_script`).

Legacy index entry (Manager main `custom-node-list.json`): `author`, `title`, `id`, `reference`, `files` (list of git URLs), `install_type` (`git-clone`), `description`, optional `pip`, `preemptions`.

Compatibility fields the registry stores per version: `supported_os`, `supported_accelerators`, `supported_comfyui_version`, `supported_comfyui_frontend_version`, `dependencies` (https://docs.comfy.org/registry/api-reference/registry/returns-a-node-version-to-be-installed.md). Manager sends `comfyui_version` and `form_factor` (`desktop-win`, `git-linux`, ...) when it fetches the catalogue (Manager main `glob/cnr_utils.py`).

## 3. Distribution and install

Three install paths exist and all end in the same place: a folder in `custom_nodes/` plus pip packages in the one ComfyUI Python environment.

1. **Registry install (the only path in the new Manager UI).** Manager calls `GET https://api.comfy.org/nodes/{id}/install?version=X.Y.Z`, gets a `NodeVersion` with `downloadUrl`, downloads the zip to an unpredictably named temp file ("security precaution"), extracts into `custom_nodes/<node_id>`, writes a `.tracking` file listing extracted files, then runs the post-install step (Manager main `glob/manager_core.py` `_cnr_install`; `glob/cnr_utils.py` `install_node`). The new UI "only supports installing nodes from the registry" and "does not support installing nodes via git" (https://docs.comfy.org/manager/pack-management.md).
2. **Git install** ("nightly" for registry packs, or any URL in the legacy UI / cm-cli): `git clone` into `custom_nodes`, same post-install. Gated (see section 7).
3. **Manual**: `git clone` or ZIP into `custom_nodes/`, then `pip install -r requirements.txt` in ComfyUI's environment. The docs warn that ZIP installs lose version control. (https://docs.comfy.org/installation/install_custom_node.md)

What runs at install time (Manager main `glob/manager_core.py` `execute_install_script`, `try_install_script`): `pip install -r requirements.txt` (each requirement passed through `pip_overrides.json` remapping and `pip_blacklist.list`; `uv` if `use_uv`), then `python install.py` from the pack root if the file exists. On Windows, or when `always_lazy_install` is set, these commands are written to `startup-scripts/install-scripts.txt` and executed at the next ComfyUI start instead (`reserve_script`). On uninstall, `uninstall.py` runs if present. At every start, each pack's `prestartup_script.py` is executed before the server is up, then `__init__.py` is imported (core `main.py`, `nodes.py`). In other words a pack has four arbitrary-code hooks: requirements wheels, `install.py`, `prestartup_script.py`, import.

Publishing (https://docs.comfy.org/registry/publishing.md; comfy-cli source https://raw.githubusercontent.com/Comfy-Org/comfy-cli/main/comfy_cli/command/custom_nodes/command.py): create a publisher at https://registry.comfy.org (GitHub sign-in), create a publishing API key per publisher, `comfy node init` writes the `pyproject.toml` skeleton, `comfy node publish` validates, zips the git-tracked files (honouring `.comfyignore` and `includes`) and uploads them to a signed URL returned by the registry (`PublishNodeVersionResponse.signedUrl`, core `comfy_config/types.py`). Alternative: GitHub Action `Comfy-Org/publish-node-action@main` triggered on pushes that touch `pyproject.toml`, with the key in a `REGISTRY_ACCESS_TOKEN` secret.

Manager itself: since 2025 it is a pip package (`comfyui_manager`) pinned by core in `manager_requirements.txt` and enabled with `--enable-manager`; Desktop ships it enabled; the git-cloned legacy Manager is disabled by the policy hook when the package is active (https://docs.comfy.org/manager/install.md; core `main.py`; Manager 4.3 `comfyui_manager/__init__.py` `should_be_disabled`). Headless: `cm-cli.py` (`install|reinstall|uninstall|update|disable|enable|fix`, `save-snapshot`, `restore-snapshot`, `cli-only-mode`, `restore-dependencies`) must run "in the same Python environment as the one running ComfyUI" (Manager main `docs/en/cm-cli.md`).

## 4. Dependencies and isolation

- **One shared Python environment** for core and every pack (venv, embedded Python of the portable build, or Desktop's environment). The official docs: "Dependency conflicts are a common issue when using ComfyUI", listing version locking, "environment pollution" ("the later installed plugin will break the existing environment") and incompatibility with core; the suggested workarounds are to loosen pins by hand, "create different Python virtual environments for different plugins", or install one plugin at a time and restart. (https://docs.comfy.org/development/core-concepts/dependencies.md)
- Manager mitigations (Manager main README and `prestartup_script.py`): `pip_overrides.json` remaps requirement strings (template maps `opencv-python` to `opencv-contrib-python-headless`, pins `numpy==1.26.4`, etc.); `pip_blacklist.list` (built-in blacklist `torch`, `torchaudio`, `torchsde`, `torchvision`); `downgrade_blacklist` (built-in: torch family, `transformers`, `safetensors`, `kornia`); `pip_auto_fix.list` restores pinned versions at startup; `use_uv`; `restore-dependencies` re-runs every pack's install scripts.
- Registry standard: "Runtime package installation through subprocess calls is not permitted." Reasoning given: Manager "will ship with ComfyUI and lets the user install dependencies", "Centralized dependency management improves security and user experience", "Helps prevent potential supply chain attacks", "Eliminates need for multiple ComfyUI reloads". (https://docs.comfy.org/registry/standards.md) The January 2025 post gave the timeline: block pip-installing subprocess in new nodes immediately, all published nodes in six months (https://blog.comfy.org/p/comfyui-2025-jan-security-update).
- The registry records a version's `dependencies` (pip strings) and Manager's risk classifier treats any pip package not already known from the catalogue as "block" (cannot be installed at any security level) (Manager main `glob/manager_server.py` `get_risky_level`).
- `comfy node validate` runs `ruff check --select S102,S307,E702 --exit-zero` and prints "We will soon disable exec and eval, and multiple statements in a single line, so this will be an error soon." — warnings, not failures (comfy-cli source, `validate_node_for_publishing`). Core's own ruff config also selects S102/S307 (core `pyproject.toml`).
- Nothing isolates a pack at runtime: no sandbox, no capability list, same process, same filesystem and network (core `SECURITY.md`, section 7). Sandboxing of the Desktop app was announced as future work in both the December 2024 and January 2025 posts; no shipped sandbox was found in the docs or source read (not confirmed).

## 5. Versioning and updates

- Registry versions are semver and **immutable**: "Once a custom node version is published, it cannot be changed." Deprecation: "More Actions > Deprecate" on the website or `PUT /publishers/{publisherId}/nodes/{nodeId}/versions/{versionId}` with `{changelog, deprecated}`; "Users who installed this version will be shown the deprecation message". (https://docs.comfy.org/registry/overview.md; https://docs.comfy.org/registry/api-reference/registry/update-changelog-and-deprecation-status-of-a-node-version.md)
- Status enums (registry OpenAPI https://raw.githubusercontent.com/Comfy-Org/registry-backend/main/openapi.yml): `NodeVersionStatus` = Active | Deleted | Banned | Pending | Flagged (plus `status_reason`); `NodeStatus` = Active | Deleted | Banned; `PublisherStatus` = Active | Banned. Admin-only `PUT /admin/nodes/{nodeId}/versions/{versionNumber}` ("Only admins can approve a node version"), `POST /publishers/{publisherId}/ban`, `POST /publishers/{publisherId}/nodes/{nodeId}/ban`. Manager lists only `Active` and `Pending` versions to the user (`all_versions_of_node` requests `statuses=NodeVersionStatusActive&statuses=NodeVersionStatusPending`).
- Installed-version bookkeeping: a registry install is recognised by `pyproject.toml` + `.tracking` in the folder, version read from `project.version` (Manager main `glob/cnr_utils.py` `read_cnr_info`); a git install is "nightly"; anything else is "unknown" (`glob/node_package.py`). Switching versions is a UI action ("select a specific version in Version", https://docs.comfy.org/manager/pack-management.md); disabled packs are moved under `custom_nodes/.disabled/` or renamed `*.disabled`.
- **Workflow files record the pack and version per node**: the frontend schema puts `cnr_id` (registry id), `aux_id` (`github-user/repo-name` for non-registry packs), `ver` (semver, a git hash of 4-40 hex chars, or `"unknown"`) and an optional `models` list into each node's `properties`; the API-format workflow carries the same three fields in `_meta` (frontend `src/platform/workflow/validation/schemas/workflowSchema.ts`, `zNodePackMetadata`, `zVersion`, `zAuxId`). Manager's "install missing nodes" reads `type`, `properties.cnr_id` and `properties.ver` from workflow JSON (Manager main `glob/manager_server.py`). The registry overview states the purpose: "The workflow JSON will store the version of the node used, so you can always reliably reproduce your workflows."
- Rollback: Manager **snapshots**. `get_current_snapshot()` returns `{comfyui: <commit>, git_custom_nodes: {url: {hash, disabled}}, cnr_custom_nodes: {id: version}, file_custom_nodes: [...], pips: {...}}`; "Update All" saves one automatically; "Restore" is applied at the next startup via `startup-scripts/restore-snapshot.json`; "for custom nodes not managed by Git, snapshot support is incomplete" (Manager main `glob/manager_core.py`; README "Snapshot-Manager").
- Compatibility: `requires-comfyui` (core version range) and `comfyui-frontend-package` pins; the registry filters by the `comfyui_version` and `form_factor` Manager sends (section 2). Core itself pins the frontend (`comfyui-frontend-package==1.49.6` in the dependencies doc) and the Manager package.

## 6. Registry design

Two generations, both still in use.

**Generation 1 (2023-2024, still consulted): a static Git index.** The Manager repository holds `custom-node-list.json` (hand-edited, "Add an entry ... and submit a Pull Request"), `extension-node-map.json` (node-class-name to repo map produced by `scanner.py`, which clones every listed repo and parses it with `ast`), `github-stats.json` (`stars`, `last_update`, `author_account_age_days`, fetched with the GitHub API by `scan.sh`), `model-list.json` and `alter-list.json`. Channels are plain raw.githubusercontent.com URLs: `default`, `recent`, `legacy`, `forked`, `dev`, `tutorial` (`channels.list.template`); `network_mode = private` lets an organisation point `channel_url` at its own copy and `offline` uses the cache. Cost to run: a GitHub repo and a cron-style script; no backend. (Manager main README "How to register your custom node", "Scanner"; `scanner.py`; https://docs.comfy.org/manager/configuration.md)

**Generation 2 (2024-): the Comfy Registry.** A hosted service at https://registry.comfy.org with API https://api.comfy.org. Data model: Publisher (1..n members) -> Node (globally unique id) -> NodeVersion (semver, immutable). (https://docs.comfy.org/registry/api-reference/overview.md) Submission: no pull request and no human in the loop at publish time; the CLI or GitHub Action uploads a zip; versions start `Pending`, the backend's `GET /security-scan` endpoint will "Pull all pending node versions and conduct security scans", and admins can set status or ban. Legacy packs were imported as "unclaimed"; a developer claims them by signing in with GitHub and proving admin rights on the repository: "Claims are automatically approved once GitHub admin permissions to the repository are verified." (https://docs.comfy.org/registry/claim-my-node.md) Search: `GET /nodes/search?search=` with `search_ranking`, `downloads`, `github_stars`, `rating` on each Node; `comfy-nodes` endpoints let Manager resolve a node class name to the pack that provides it ("Retrieve a node by ComfyUI node name"). (registry OpenAPI; https://docs.comfy.org/llms.txt index)

Who runs it and what it costs: Comfy Org (the company; co-founder Robin Huang maintains the registry per the search summary, not independently confirmed). Infrastructure per the backend README: Go, Supabase/Postgres, Google Cloud (Firebase auth, signed Cloud Storage URLs, a Cloud Function for scanning): "We keep the security scan code private to avoid exploiters taking advantage of it." (https://raw.githubusercontent.com/Comfy-Org/registry-backend/main/README.md) Running cost is not published (not confirmed). Comfy Org announced $30M at a $500M valuation on 2026-04-24, "$47 million" total (vendor blog, market fact). Publishing is free; the docs mention no fee and no revenue share (none found; "not confirmed" only in the sense that no pricing page exists).

Review steps actually visible: automated scan of pending versions; `comfy node validate` warnings before upload; admin approve/ban; a `#security-review-council` Discord channel announced for flagged findings (January 2025 post). Manager still reads the Generation-1 `custom-node-list.json` to classify unknown git URLs and unknown pip packages as "high" and "block" risk respectively (Manager main `glob/manager_server.py` `get_risky_level`).

## 7. Trust and permissions

- **Threat model (core `SECURITY.md`)**: ComfyUI "is designed to run locally", binds to `127.0.0.1`; "The user has not installed untrusted custom nodes. Custom nodes are arbitrary Python code and are trusted as much as any other software the user chooses to install." Issues "that require a specific custom node to be installed" and "Issues requiring `--listen`" are explicitly out of scope. There is **no declared-permission model at all**: a pack runs in the server process with the server's filesystem, network and GPU access.
- **Manager `security_level`** (`strong` | `normal` (default) | `normal-` | `weak`) gates Manager *operations*, not pack behaviour. Risk tiers: high = install via git URL, pip install, packs not in the default channel, "fix" custom nodes; middle = uninstall/update, install packs in the default channel, restore/remove snapshot, restart; low = update ComfyUI. `normal-` allows high-risk features only when the server listens on `127.*`. (https://docs.comfy.org/manager/configuration.md; Manager main README) Desktop labels these Strict / Standard / Relaxed / Permissive (https://docs.comfy.org/manager/install.md).
- **Dedicated install flags (Manager main, unreleased changelog and README)**: `allow_git_url_install` and `allow_pip_install` in `config.ini`, both default `false`, "take effect only when the server listens on a loopback address", read once at startup; `allow_flagged_nodepack_install` likewise for registry versions whose status is `Flagged`. "the flags never widen the exposure of a public deployment." Risk `block` (unknown pip package) "cannot be installed at any security_level". The docs are not yet consistent: `manager/troubleshooting.md` still tells users to set `security_level = weak` to install via git URL, while the README says those surfaces are "no longer governed by `security_level`".
- **Config hardening**: Manager v3.38 moved its data to `user/__manager/` (a path core protects from the web API) because with `--listen 0.0.0.0` the old `user/default/ComfyUI-Manager/` "may have been tampered with by malicious actors"; on migration a level below `normal` is raised to `normal` "because the security level setting itself may have been tampered with"; on an outdated core, `strong` is forced and "All installations are blocked". (Manager main `docs/en/v3.38-userdata-security-migration.md`) Manager 4.3 adds a request middleware that records every client IP that has called a Manager endpoint; once more than one IP has connected, handlers tagged `MULTIPLE_REMOTE_BAN_NON_LOCAL` or `MULTIPLE_REMOTE_BAN_NOT_PERSONAL_CLOUD` are refused with HTTP 403 "This request is banned", and a `personal cloud` network mode (also exposed in Desktop's Manager Network Mode setting) relaxes the second rule (Manager 4.3 `comfyui_manager/__init__.py` `create_middleware`; https://docs.comfy.org/manager/install.md).
- **"Verified" in practice.** The registry overview promises: "All nodes will be scanned for malicious behaviour such as custom pip wheels, arbitrary system calls, etc. Nodes that pass these checks will have a verification flag (check) beside their name." In the frontend code the check icon (`VerifiedIcon`) is rendered for every version option that is not `nightly`, has no conflict and is not `Flagged`; `Pending` versions get the icon plus a "pending" label (frontend `PackVersionSelectorPopover.vue`, `PackStatusMessage.vue`). So the badge means "not flagged by the scanner", not "author identity verified". A "Verification process for custom node authors" was a January 2025 roadmap item; nothing in the docs or OpenAPI read today exposes an author-verification state (not confirmed as shipped).
- **Blocklists at startup**: Manager's `security_check.py` runs before core loads nodes; it hard-codes `ComfyUI_LLMVISION` (folder, pip author `AppleBotzz`, `%LocalAppData%\rundll64.exe`), `lolMiner`, `ultralytics==8.3.41/8.3.42` and `litellm==1.82.7/1.82.8`, prints remediation steps and calls `exit(-1)`: "Malware has been detected, forcibly terminating ComfyUI execution." (Manager main `glob/security_check.py`)
- **Remote disable**: core calls `comfyui_manager.should_be_disabled(path)` for every pack and logs "Blocked by policy"; in Manager 4.3 the function only blocks folders whose name contains `comfyui-manager` (the legacy clone) and carries the comment "The blocklist can be expanded later based on policies." The "Manager mechanism to remotely disable malicious nodes" from the January 2025 roadmap is therefore a hook, not a live kill switch (Manager 4.3 `comfyui_manager/__init__.py`; core `main.py`, `nodes.py`).
- **Standards**: `eval`/`exec` "prohibited", runtime pip via subprocess "not permitted", "Code obfuscation is prohibited" ("Impossible to review and likely to be malicious"); plus community-value, no interference with other packs, legal compliance, maintained, fork naming rules. (https://docs.comfy.org/registry/standards.md)
- **User-facing warning**: the install guide tells users to "Only install custom nodes from trusted authors and those commonly used by the community" (https://docs.comfy.org/installation/install_custom_node.md). Manager's own disclaimer: it "does not guarantee their proper functioning."
- Other: `--disable-all-custom-nodes` with `--whitelist-custom-nodes` for bisecting (core `comfy/cli_args.py`; https://docs.comfy.org/troubleshooting/custom-node-issues.md); `cli-only-mode` disables the Manager web API "for security or policy reasons".

## 8. Models

- **Location**: a fixed set of typed folders under `models/` registered in core `folder_paths.py` (`checkpoints`, `loras`, `vae`, `text_encoders`, `diffusion_models`, `controlnet`, `upscale_models`, `detection`, `audio_encoders`, `optical_flow`, ... each with allowed extensions). `supported_pt_extensions = {'.ckpt', '.pt', '.pt2', '.bin', '.pth', '.safetensors', '.pkl', '.sft'}`, i.e. pickle-based formats are accepted by core. `--base-directory` and `--models-directory` relocate everything.
- **Sharing across installs**: `extra_model_paths.yaml` (loaded from the core folder and any `--extra-model-paths-config`) adds search paths per folder name with `base_path`, multi-line lists and `is_default: true` ("listed first, and used as the default dirs for eg downloads"); it can also add `custom_nodes` paths and a1111 layouts. The loader is `utils/extra_config.py` -> `folder_paths.add_model_folder_path(name, path, is_default)`. Desktop keeps this in `extra_models_config.yaml` under the user's AppData. (core `extra_model_paths.yaml.example`; https://docs.comfy.org/development/core-concepts/models.md)
- **How a node references a model**: by `(folder_name, filename)`. Loader nodes build a dropdown from `folder_paths.get_filename_list(folder)` and resolve with `get_full_path_or_raise(folder, filename)` (raises `FileNotFoundError("Model in folder ... not found")`). A pack can register its own folder with `add_model_folder_path`. The workflow stores the filename in the node's widget values; a node may additionally carry a `properties.models` list whose entries are `{name, url, directory, hash?, hash_type?}` (frontend schema `zModelFile`; "Only `name` is required", and "a workflow that failed it still loads"). That optional entry is the only provenance field found; core's `folder_paths.py` keeps no hash, revision or source record for files on disk, and Manager's downloader does not verify a hash (no verification code found in `glob/manager_downloader.py`; inferred).
- **Download prompts**: Manager's "Install Models" dialog is driven by `model-list.json` entries `{name, type, base, save_path, description, reference, filename, url, size}`; downloads go through `torchvision.datasets.utils.download_url` or aria2, with `HF_ENDPOINT` rewriting Hugging Face URLs; whole HF repos are streamed file by file from `/resolve/main/` into a local folder (not via the Hugging Face cache). Model installs require security level `middle`; downloading a file that is not `.safetensors` and not in the default model list requires `high` ("Downloading models not in '.safetensors' format is only allowed for models registered in the 'default' channel at this security level"). (Manager main `glob/manager_server.py` `install_model`; `glob/manager_downloader.py`; README) The `/api/workflow_templates` and template browser surface model download prompts for first-party templates (docs; not read in detail).
- Core's `app/model_manager.py` exposes `/experiment/models` listing and reads safetensors headers for previews; `SECURITY.md` excludes "`torch.load` and related deserialization issues in old PyTorch versions" from scope.

## 9. Local, remote or both

Both, with local as the default. The server binds to `127.0.0.1:8188`; `--listen` exposes it; the browser UI is a separate client (so UI remote / compute local is normal); "API mode" lets any client post a workflow. Comfy Cloud runs workflows on hosted GPUs and partner (API) nodes call external providers; comfy-cli routes "local or cloud" per command. (https://docs.comfy.org/custom-nodes/overview.md; core `comfy/cli_args.py`; https://docs.comfy.org/comfy-cli/getting-started.md) Whether community custom nodes run on Comfy Cloud was not established (not confirmed).

## 11. Borrow

1. **Manifest shape.** A single `pyproject.toml`-style file with an immutable `name` (= id), semver `version`, `PublisherId`, `requires-<app>` range, OS/accelerator classifiers and a `Repository` URL. Clips Kitty's manifest can mirror the field semantics (immutable id, publisher namespace, compatibility range, classifiers) while staying JSON/YAML. (Section 2)
2. **Immutable versions + a status enum per version.** `Pending -> Active | Flagged | Banned | Deleted`, `deprecated` + `status_reason`, and a manager that lists only Active/Pending and refuses Flagged unless the user opts in on loopback. This is the cheapest honest "trust" signal: it describes what the registry did, not what the author is. (Sections 5, 7)
3. **Record the pack id and version in the artefact.** ComfyUI writes `cnr_id`/`aux_id` + `ver` into every node of a workflow so "install missing" and reproduction are possible later. Clips Kitty's job files and presets should record `publisher/pipeline@version` (and the model identifiers) the same way, and the manager should offer "install what this file needs" from a class-name/capability -> pack map built at index time. (Section 5)
4. **Snapshots.** One JSON of `{app version, packs: {id: version | git hash}, pips}` saved automatically before "Update All" and restorable at next start is the rollback story users actually use. (Section 5)
5. **Loopback-only, default-deny switches for risky operations**, read once at startup, with the rule "the flags never widen the exposure of a public deployment", and a separate network mode (`public | private | offline`) so organisations can mirror the index. Clips Kitty's engine already binds to 127.0.0.1; the same gate fits. (Section 7)
6. **Start with the Generation-1 index.** ComfyUI ran for about two years on a Git repo with `custom-node-list.json` (by PR), a scanner that derives the node map, and `github-stats.json` with stars, last update and author account age fetched at build time. That is exactly H3 and it cost nothing; it only broke down on versioning and scanning, which the status enum above addresses. (Section 6)
7. **Ownership by GitHub admin check** for claiming/first publish, automatic and instant; and `.comfyignore` + "publish only git-tracked files" so the published archive equals the repo at a commit. (Sections 3, 6)
8. **Startup blocklist with hard stop.** A tiny, versioned list of known-bad packages/files checked before any pack loads, with printed remediation. Cheap and effective after the fact. (Section 7)
9. **Conventions, not features**: `example_workflows/`, node help pages, `node_list.json`-style explicit capability lists, `preemptions` to resolve name collisions. (Sections 1, 2)
10. **Counts**: the registry counts downloads server-side at the install endpoint and copies GitHub stars; comfy-cli telemetry is opt-out via `DO_NOT_TRACK`. For Clips Kitty (opt-in telemetry), GitHub-derived stars/last-updated at index build are the free part (H10). (Section 6)

## 12. Avoid

1. **In-process import of arbitrary plugin Python with four code hooks** (`requirements.txt` wheels, `install.py`, `prestartup_script.py`, `__init__.py`). Every incident above used one of them. Clips Kitty's plugins should talk to the existing API out of process (H1) and declare, not run, installation.
2. **One shared Python environment that plugins mutate.** The overrides/blacklists/auto-fix machinery in Manager is the cost of that choice; the docs still tell users to make one venv per plugin by hand.
3. **A badge whose code meaning is "not flagged" presented as "verified".** Clips Kitty's fixed decision ("Verified" only if a real process exists) means naming it "scanned" or "not flagged" instead.
4. **Accepting pickle model formats by default** (`.ckpt`, `.pt`, `.pkl`, `.bin`) and gating only the download dialog. Prefer safetensors and warn on pickle at load time (H7).
5. **Security settings stored where the web API can write them.** Manager had to migrate its config to a protected path and force-raise the level after discovering tampering via `--listen`.
6. **A global flat namespace for node class names.** Collisions are handled after the fact by "Conflicted Nodes" and `preemptions`; use `publisher/pipeline` ids and capability names from day one (H8).
7. **Shipping code-execution nodes without a permission story.** The Censys campaign abused ordinary "run Python" packs on exposed instances; Clips Kitty's permission list must be host-enforced or not called a permission (H5).
8. **Depending on the hosted registry for the only install path.** The new Manager UI cannot install from a git URL at all; Clips Kitty's fixed decision is GitHub-at-a-pinned-ref plus a free index, so the registry should never be a hard dependency for installing.
9. **Documentation drift about security switches.** Three pages currently describe three different meanings of `security_level` for git-URL installs. Keep one source of truth and version the security docs with the app.
10. **Deferring scanning to a private cloud function.** Keep Clips Kitty's checks (manifest validation, banned-call linting, pinned-ref verification) runnable locally and in CI so a developer sees the same result the index sees.

## Hypotheses

- **H1 (out-of-process plugins over the local API are lowest risk): supported by negative evidence.** ComfyUI is the in-process counter-example: packs import into the server with four code hooks (section 3), the threat model declares them trusted (SECURITY.md), and every incident in section 10 ran through that path. ComfyUI's only structural answer so far is a roadmap item (Desktop sandbox, 2024-12 and 2025-01 posts), not shipped.
- **H2 (smallest useful contract: video in, scored ranges out): partly supported.** ComfyUI's contract is one typed function per node (`INPUT_TYPES`/`RETURN_TYPES`), which shows that a small typed I/O contract is enough to seed an ecosystem; it does not speak to the video-specific shape.
- **H3 (static Git registry, PR-submitted, CI-built index, $0): confirmed, with a known ceiling.** Generation 1 of the Manager index is exactly this (section 6) and ran for about two years. ComfyUI outgrew it for two reasons: no immutable versions and no scanning. Both can be added to a static index (status fields per version, CI lint) before a backend is needed.
- **H4 (hand review does not scale): confirmed.** With "60,000+ nodes" (vendor claim) there is no human review at publish; the registry runs an automated scan over pending versions and keeps admin approve/ban endpoints; `comfy node validate` only warns (sections 4, 6, 7).
- **H5 (declared permission is not an enforced one): confirmed in the strongest form.** ComfyUI declares nothing and enforces nothing at runtime; the Manager's levels gate installs, not behaviour (section 7). The Censys campaign shows what a code-execution pack means on an exposed instance.
- **H6 (ComfyUI standards prohibit runtime pip, eval/exec, obfuscation after 2024 incidents; shared env invites conflicts): confirmed verbatim.** Standards page quotes in section 4/7; the dependencies doc admits conflicts are "a common issue" and suggests per-plugin venvs by hand.
- **H7 (HF revision pins; safetensors preferred; warn on pickle): partly informed.** ComfyUI does not use the HF cache or revisions at all: it streams files by URL into flat typed folders and records only filenames (section 8). It does prefer safetensors (download gate) but core still loads `.ckpt/.pt/.pkl/.bin`. No evidence on Windows symlinks here.
- **H8 (namespaced ids + declared capabilities with typed I/O let implementations coexist): supported.** Registry node ids are globally unique and publisher-scoped, and workflows carry `cnr_id`/`aux_id`; but node *class* names are a flat global namespace resolved by last-import-wins and `preemptions` (section 1), which is the failure mode H8 avoids.
- **H9 (Eklipse/Overwolf): not addressed by this platform.**
- **H10 (install/usage counts need telemetry; stars/last-updated from GitHub at build time; opt-in): confirmed.** The registry counts `downloads` server-side (the install endpoint) and exposes `github_stars`, `rating`, `search_ranking`; the legacy index fetched `stars`, `last_update`, `author_account_age_days` with the GitHub API in `scan.sh`; comfy-cli telemetry is opt-out (`DO_NOT_TRACK`), which Clips Kitty's opt-in rule would invert (section 6).
