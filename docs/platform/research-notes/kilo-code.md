# Kilo Code — Marketplace and extension ecosystem

- Platform: Kilo Code (Kilo-Org/kilocode; VS Code extension, JetBrains plugin, CLI). Acquired by Anaconda, announced 2026-07-15.
- Tier: 1 (Track A)
- Date read: 2026-10-06
- Brief's question: what should the Marketplace and extension ecosystem look like?

**Verdict (two lines):** Kilo's marketplace is a Git monorepo with one metadata file per item, PR-only submission, CI-generated catalogs and strict validators, served to clients through a thin pass-through API with a one-hour cache; it is cheap, honest about risk ("Marketplace validation is not a security review") and has a careful installer, but it has no version field, installs skills from a mutable `skills-latest` archive, has no update or rollback, vendors third-party skills into the registry, and runs plugins in-process with hooks that can silence the permission system.
Clips Kitty should borrow the registry layout, generators, install dialog, staging/receipt mechanics and the wording; it should not borrow the mutable archive, the vendoring, the flat id namespace or the in-process plugin model.

## 1. Unit of extension

Four item types, plus a legacy fifth (read 2026-10-06, https://kilo.ai/docs/customize/marketplace and the kilo-marketplace README):

| Type | What it is | Where it lands (project / global) |
|---|---|---|
| Agent | Markdown file with YAML frontmatter: prompt + `mode` + `permission` rules | `.kilo/agents/<name>.md` / `~/.config/kilo/agents/<name>.md` |
| Skill | Folder with `SKILL.md` (Agent Skills spec, agentskills.io) plus optional `scripts/`, `references/`, `assets/`, `examples/`; shipped as `.tar.gz` | `.kilo/skills/<name>/` / `~/.kilo/skills/<name>/` |
| MCP server | A JSON config fragment: local stdio command (`npx`, `uvx`, `docker`) or remote `streamable-http` URL, with `{{PARAM}}` placeholders | entry under `mcp` in `.kilo/kilo.json` / `~/.config/kilo/kilo.json` |
| Plugin | TypeScript/JavaScript module loaded in-process at startup; hooks, custom tools, auth and model providers; from npm or a public git repo | specifier added to the `plugin` array in `.kilo/opencode.json` and/or `.kilo/tui.json` (global equivalents under `~/.config/kilo/`) |
| Mode (legacy) | `modes/marketplace.yaml` "retained for legacy Kilo 5.x clients only. It is not actively maintained." (modes/README.md) | n/a |

The docs stress: "Marketplace items are configuration, instruction, and plugin files, not VS Code extensions."

Registry contents at clone commit ff51758b (2026-09-28): 128 MCPs, 191 skills, 8 agents, 2 plugins (one of which is Kilo's own test fixture).

## 2. Manifest / metadata format

One file per item, in a directory named after the id. Real field names from the repository (clone read 2026-10-06):

**`mcps/<id>/MCP.yaml`** (CONTRIBUTING.md "MCP Properties"): required `id`, `name`, `description`, `author`, `url`, `category`, `content`; optional `suggest_for.filename` / `suggest_for.vscode_extension`, `requirements`, `skills` (companion skill ids), `prerequisites`, `parameters` (`name`, `key`, `placeholder`, `optional`). `content` is a list of installation methods `{name, prerequisites, content: <JSON string>}`; the JSON is either `{"command","args","env"}` (stdio) or `{"type":"streamable-http","url","headers"}`. Categories are a closed set (`business`, `data`, `development`, `observability`, `productivity`, `search`, `web-automation`); the generator rejects others.

**`skills/<id>/SKILL.md`** frontmatter (AGENTS.md, CONTRIBUTING.md): `name` (must equal directory), `description`, `license` (SPDX) **or** `metadata.source.license_path` ("not both"), `metadata.category`, `metadata.author`, `metadata.version` (optional, free semver string), `metadata.suggest_for`, `requirements`, `compatibility` (free text), and for contributed skills `metadata.source.repository`, `metadata.source.path`, `metadata.source.license_path`, `metadata.source.ref` (optional), `metadata.source.commit` ("Full 40-character Git SHA of the imported upstream revision; managed by marketplace tooling"). The updater keeps only `name, description, license, allowed-tools, metadata, compatibility` in frontmatter (bin/update-skills.ts `allowedFrontmatterFields`).

**`agents/<id>/AGENT_DEFINITION.md`** frontmatter (e.g. agents/architect): `id`, `name`, `description`, `author`, `category`, `mode` (`primary`|`subagent`|`all`), `permission` (map of tool → `allow`|`ask`|`deny` or glob map), optional `requirements`.

**`plugins/<id>/PLUGIN.yaml`** (plugins/README.md): required `id`, `name`, `description`, `category`, `author`, `url`, `content`; `tags` forbidden (derived). For npm: `id` = exact package name, `content` = `name`, `name@1.2.3`, `name@^1.2.0`, `name@next`. For git: `content` = `git:<repo>[@ref][#subpath]` and `id` = normalised identity `git/<host>/<owner>/<repo>[/subpath]`.

**Shared `requirements`** (CONTRIBUTING.md "Marketplace Requirements"): subgroups exactly `skills`, `vscode_extensions`, `mcps`; ids checked against the registry at generation; self-reference rejected; "Dependencies between multiple resources are not expanded or checked for cycles."

**Compatibility fields:** none in the catalog. Plugins may declare `engines.opencode` in `package.json`; "If the running CLI does not satisfy the range, the plugin is skipped and a warning is surfaced" (plugins docs). Companion skills "require a client with bundle support"; older clients "ignore the companion list".

**Generated catalog shape** (`<type>/marketplace.yaml`, `linguist-generated=true` in .gitattributes): `items[]`. Skill items carry `id`, `description`, `category`, `githubUrl`, `rawUrl`, `content` (archive URL). MCP/plugin/agent items carry their source fields plus `tags: [category]`; agent `content` embeds `mode`, `description`, `prompt`, `permission`. No version, no date, no counts (bin/generate-*.ts; packages/opencode/src/kilocode/marketplace/schema.ts).

## 3. Distribution and install

**How the client gets the index.** `packages/opencode/src/kilocode/marketplace/api.ts` (kilocode clone, read 2026-10-06): `DEFAULT_BASE_URL = "https://api.kilo.ai/api/marketplace"`, overridable by `KILO_MARKETPLACE_BASE_URL` ("a test/enterprise override"); paths `agents`, `mcps`, `skills`, `plugins`; 10 s timeout, 3 retries with back-off, 5-minute in-process cache. Probed 2026-10-06: `https://api.kilo.ai/api/marketplace/mcps` → 200, `application/x-yaml`, `cache-control: public, max-age=3600, s-maxage=3600`, `server: Vercel`; the body is the committed `mcps/marketplace.yaml` byte-for-byte in shape (CONTRIBUTING.md: "The `/api/marketplace/mcps` API passes generated YAML through unchanged"; "allow for the API's one-hour cache"). So: Git index → CI-generated YAML → thin pass-through HTTP endpoint, not raw GitHub (the `rawUrl`/`githubUrl` fields are for display only).

**What runs at install** (installer.ts, skill-archive.ts, companions.ts, git-source.ts):
- Skill: download `content` tarball (60 s timeout), extract with `tar -xzf --strip-components=1 --no-same-owner --no-same-permissions` into a `.staging-<id>-*` dir under the skills dir, reject escaped paths and symlinks, reject an archive that ships the ownership file `.kilo-marketplace.json`, require `SKILL.md`, then atomic `rename` into place. For companion skills (strict mode) the archive is listed *before* extraction: only regular files and directories, no `..`, no control chars, no Windows device names, one top-level directory, no duplicates; frontmatter is parsed as plain YAML because "gray-matter … JavaScript engine uses eval, so an archive with `---javascript` would execute code during staging". Nothing in the skill executes at install (docs: "Installing a bundle does not approve MCP tool calls or run scripts included in a skill"; CONTRIBUTING: "installation does not execute them").
- MCP server: `{{KEY}}` parameters substituted (JSON-escaped), JSON parsed, normalised to `{type:"local", command:[...]}` or `{type:"remote", url}` and written under `mcp.<id>` in the scoped config. The server command (`npx -y …`, `uvx …`, `docker run …`) runs when Kilo next loads MCP config, which is where third-party code first executes. Companion bundle: skills staged first, a receipt `{version:1,id,token,config,base,skills}` written to `.kilo/marketplace/mcps/<id>.json` (global: `~/.config/kilo/marketplace/mcps/`) so removal can delete owned skills "even when the catalog is unavailable or has changed".
- Plugin: identity derived from spec must equal catalog `id`; npm spec staged with Bun ("Install scripts are disabled for npm plugins. Kilo installs packages with lifecycle scripts such as `install` and `postinstall` blocked", plugins docs); `package.json` read for `./server` / `./tui` targets; specifier inserted into the JSONC `plugin` array under a file lock. Git spec: `git clone --depth 1 -- <repo>`, then `fetch --depth 1 origin -- <ref>` and `checkout --detach FETCH_HEAD`, `rev-parse HEAD` stored in a marker JSON next to the cache dir `~/.cache/opencode/packages/git/<identity>-<sha1 of identity@ref>`, `.git` deleted. "Kilo does not install npm dependencies for git plugins."
- Agent: frontmatter + prompt written as a Markdown file.

**User-facing flow** (docs + InstallModal.tsx): the dialog shows scope (project/global), the destination path, prerequisites, the chosen installation method and parameter inputs "before it changes anything"; companion skills and their destinations are listed; a toast warns if sessions are busy ("install anyway" / cancel). Install fails if the item already exists in that scope ("Remove it first."). Removal is per scope and deletes "its marketplace-managed entry". After install/remove "Kilo reloads the affected configuration. Running sessions may be interrupted".

**Contribution / publishing steps** (CONTRIBUTING.md, plugins/README.md, plugins docs): fork → add `mcps/<id>/MCP.yaml` or `plugins/<id>/PLUGIN.yaml`, or for a skill host it in your own public repo and run `npx tsx bin/add-remote-skill.ts <github url>` (sparse checkout, copies into `skills/<id>/`, stamps `metadata.source`) → run generators/tests → PR. "Contributions are accepted through pull requests only"; "Skills submitted without a valid `metadata.source` referencing an external repository will not be accepted unless they are official Kilo skills." Companion-skill publishing order is five steps and warns that "merging a new skill and its first MCP reference together can expose a download URL before its asset exists."

**Automated checks** (.github/workflows): `validate-skills.yml` runs `skills-ref validate` (pip-installed from agentskills/agentskills) on every skill on PR and push; `generate-marketplace.yml` on `pull_request` regenerates all four catalogs, runs `pnpm test`, `typecheck:plugins`, `typecheck:mcps`, and commits `chore: regenerate marketplace.yaml` back to the PR branch with `contents: write` (this cannot push to fork branches with the default token, so contributors are told to regenerate themselves — inferred); `package-skills.yml` on push to `main` tars every skill (excluding `evals`, `local.patch`, `local.remove`), creates a timestamped GitHub release `skills-<date>-<sha>` and re-uploads all archives with `--clobber` to the mutable `skills-latest` release.

## 4. Dependencies and isolation

- Skills: no dependency mechanism; `requirements` is declarative only. Bundled scripts run later through the agent's normal tool permissions. Embedded `` !`command` `` placeholders execute only for skills in trusted locations (global dirs, built-ins); "Project skills (`.kilo/skills/` in a repository) and skills fetched from remote URLs never execute commands" and trusted ones list every command in one prompt first; `KILO_DISABLE_SKILL_SHELL` kill switch (skills docs).
- MCP servers: each is a separate process started by `npx`/`uvx`/`docker` (local) or a remote HTTP service; isolation is whatever those tools provide (uvx makes a per-package env; npx uses its cache; docker a container). Of 128 MCP.yaml files: 49 mention `npx`, 39 `uvx`, 27 `docker`, 31 `streamable-http` (grep counts, overlapping). Secrets via `env` placeholders; docs warn to "Prefer environment-variable references for secrets, and review `.kilo/kilo.json` before committing it."
- Plugins: in-process inside the Kilo server (Bun). npm plugins and their dependencies share one cache `~/.cache/opencode/packages/`; "Duplicates (same package, same version) are deduplicated. Hooks from multiple plugins run sequentially in load order." Local plugins get `bun install` at startup from `.kilo/package.json`. Git plugins must vendor dependencies. `KILO_PURE=1` disables all external plugins.
- Conflicts: no resolver; ids are unique per type at generation time (`Duplicate skill name`, `duplicate MCP id` errors in bin/).

## 5. Versioning and updates

- Catalog: no version field for skills, MCPs or agents. Plugin `content` may carry an npm version/range/tag or a git ref; the client treats only a 40-hex SHA as immutable (`isImmutableRef`); branch/tag/default refs are re-cloned after a 1-hour TTL ("A mutable ref is re-checked after this long so branch installs can pick up fixes"). "Pinned npm versions like `my-plugin@1.2.3` install that exact version and do not check for newer registry versions. Bare package names resolve to `latest` and can refresh when the cached copy becomes stale."
- Skills: the archive URL is always `releases/download/skills-latest/<id>.tar.gz` (bin/marketplace-generator-utils.ts `archive()`), a release whose assets are overwritten on every main push; timestamped releases exist but nothing references them. The registry pins the upstream `metadata.source.commit`, and `bin/update-skills.ts` re-syncs from upstream by sparse checkout, re-applying maintained overlays `local.patch` (64 of 191 skills) and `local.remove` (2). "The marketplace periodically syncs with source repositories."
- Update flow in the client: none. Install refuses when already present ("Skill already installed. Uninstall it before installing again."), so update = remove + reinstall (inferred from installer.ts). No rollback.
- Deprecation: modes catalog frozen for 5.x; `requirements.skills` kept with "its existing meaning" when `skills` (companions) was added.

## 6. Registry design

- Central service: minimal. Source of truth is the public Git repo Kilo-Org/kilo-marketplace (Apache-2.0; GitHub page read 2026-10-06: 187 stars, 205 forks, 418 commits, 14 open issues, **183 open pull requests**). Index built by GitHub Actions, published as committed YAML and as GitHub Release assets, fronted by a Vercel endpoint at `api.kilo.ai/api/marketplace/<type>` (the same bytes are served from `kilo.ai`, `app.kilo.ai`, `api.kilocode.ai`) with a one-hour CDN cache.
- Submission and review: PR only. `REVIEW.md` is a reviewer (and AI-reviewer) policy: "Reviews are read-only", "Use all 6 [sub-agents] for multi-package imports" sharded into provenance/licensing, scripts/hooks/binaries, packaging, domain correctness, "injection, secrets, subprocesses, network actions, cost, and consent", and activation quality; findings graded Critical/Warning; "CI passing alone does not prove examples, formulas, security, licenses, updater behavior, or bundled resources correct."
- Cost to run: GitHub Actions and Releases on a public repo (no charge), one serverless pass-through endpoint, plus maintainer review time (the 183-PR backlog is the visible cost).
- Discovery aids in the catalog: `category`, `suggest_for.filename` / `vscode_extension` (client matches workspace files, `relevance.ts`), `prerequisites`, `requirements`, `author`, `url`. No stars, downloads, dates or ratings.

## 7. Trust and permissions

- Tiers / "verified": none. The schema has no trust field; items show `author` and `url`. The README calls the collection "curated"; the docs say "Marketplace validation is not a security review."
- Declared permissions: agents declare `permission` (allow/ask/deny with glob maps, "the last matching rule wins"); MCP tools are gated per tool as `{server}_{tool}` with the same actions and a Permission Dock prompt ("Approve Always" writes an allow rule). `.env` reads stay prompted even under broad allows. These are evaluated by the runtime at call time, so for agents and MCP tools a declared rule is an enforced gate — but Kilo's own SECURITY.md says: "Kilo CLI does **not** sandbox the agent. The permission system exists as a UX feature … it is not designed to provide security isolation." and lists "MCP server behavior" and "Malicious config files" as out of scope.
- Plugins: no permission model. Docs: "Plugins run code with full permissions. A plugin can read and change your files, run commands, and access your credentials and network. Install only plugins that you trust, and review the plugin source and its dependencies before you install it." Hooks include `permission.ask` ("Auto-allow or auto-deny permission prompts"), `tool.execute.before` (mutate args), `chat.headers`, `shell.env`, `auth`, `provider` — a malicious plugin can approve every prompt, rewrite commands, inject env vars into every shell command and add headers to LLM calls. The VS Code network-restriction setting text confirms plugins sit outside it: "trusted plugin hooks remain outside this restriction" (webview-ui/src/i18n/en.ts). Mitigations are perimeter-only: npm lifecycle scripts blocked, `engines` check, `KILO_PURE=1`, cache-path and ref-injection hardening in git-source.ts.
- MCP servers: a local server is "a command as a child process on your machine" running with the user's privileges; a malicious `npx -y` package executes arbitrary code at first start, before any tool permission prompt (inferred from the install content format; the docs' only pre-install advice is "Review the item's author, source link, prerequisites, requested parameters, and available tools").
- Organisation controls: "Enterprise MCP Controls" is a design doc: "Proposal - no matching organization MCP allowlist implementation exists yet."
- Kilo's permission documentation: confirmed. It lives at /docs/customize/agent-permissions, /docs/getting-started/settings/auto-approving-actions and /docs/automate/mcp/using-in-kilo-code (read 2026-10-06 via kilo.ai/docs/llms.txt). The raw-markdown endpoint those links point to (`kilocode-docs.vercel.app/api/raw-markdown?path=…`) returned NOT_FOUND: not confirmed by that route.

## 8. Models

The marketplace distributes no models. Plugins can "Register model providers — dynamic model catalogs" (`provider` hook); the bundled `@kilocode/plugin-atomic-chat` discovers local models via `GET /v1/models` only when opted in (docs llms.txt). Model weights are the user's provider's concern. Not comparable to Clips Kitty's model manager.

Note the unrelated commercial page at https://kilo.ai/marketplace (read 2026-10-06): coding plans and partner apps paid "with your Kilo Credits … No separate billing, no extra accounts." It is a billing marketplace, separate from the extension registry studied here.

## 9. Local, remote or both

Both. MCP servers are local (stdio child process) or remote (`streamable-http`, 31 of 128 entries; OAuth supported, e.g. `mcps/anaconda`). Skills, agents and plugins are local files/processes. Clips Kitty's "local, remote and hybrid are all legitimate" maps directly onto Kilo's local/remote MCP split.

## 11. Borrow

1. **Registry layout and generators.** One `pipeline.yaml`-style file per item under `<type>/<id>/`, directory name = `id`, closed category set, typed `requirements` resolved against the index at build time, self-reference rejected, generated `index` committed with `linguist-generated=true` and a "do not edit manually" header (bin/*.ts, .gitattributes). Add what Kilo lacks: a `version`, a pinned `ref`/`commit` and an index build date.
2. **Install dialog and mechanics.** Show scope, destination paths, prerequisites and parameters before writing anything; stage in a sibling temp dir and `rename` atomically; inspect archives before extraction (links, traversal, device names, one root, duplicates); refuse archives that carry the installer's own ownership file; parse manifests with a plain YAML parser, never a front-matter library with code engines; keep an ownership receipt per install so removal works when the registry has changed (skill-archive.ts, companions.ts).
3. **Git source spec and identity.** `git:<repo>[@ref][#subpath]` with option-injection-safe ref validation, `git/<host>/<owner>/<repo>[/subpath]` identities that cannot collide with package names, a 40-hex SHA treated as immutable and a recorded `sha` marker for everything else (git-source.ts). Clips Kitty should require the SHA at index-build time rather than allow mutable refs.
4. **Provenance fields.** `metadata.source.{repository,path,commit,license_path}` and the rule that a contributed item is not accepted without an external canonical source and a licence file (CONTRIBUTING.md).
5. **Honest wording.** "Marketplace validation is not a security review"; "Plugins run code with full permissions"; a SECURITY.md threat model that says prompts are UX, not isolation. Matches the owner's rule "never hide a security or permission risk".
6. **Trusted vs untrusted locations for anything that executes** (embedded skill commands run only from trusted dirs, every command listed in one prompt, env kill switch) and a `KILO_PURE`-style switch to boot with no third-party code.
7. **Mirror override** (`KILO_MARKETPLACE_BASE_URL`) so a user or org can point the client at their own index.

## 12. Avoid

1. **Mutable "latest" artefacts.** `skills-latest` is overwritten on every main push and the catalog has no version, so a client cannot pin, diff or roll back, and a bad upstream sync ships to everyone within an hour. Clips Kitty's fixed decision (install at a pinned ref, rollback) is the opposite; keep per-version assets and never reference a mutable tag.
2. **Vendoring third-party content into the registry.** Kilo copies skills in, then maintains `local.patch` overlays for 64 of 191 skills and a periodic re-sync; the registry becomes a fork of everyone's repo (licence checks, drift, review load). Clips Kitty's registry should hold metadata only and point at the developer's repo at a commit.
3. **In-process plugins with hooks over the permission system.** A plugin that can implement `permission.ask`, `tool.execute.before` and `shell.env` can neutralise every safeguard silently. Clips Kitty pipelines should stay out-of-process over the local API with no hook into the host's permission decisions.
4. **A flat id namespace** for skills/MCPs (first PR wins the name; collisions only caught by the generator). Use `publisher/pipeline`.
5. **"Remove it first" instead of update.** Provide update, enable/disable and rollback as first-class actions with the old version kept.
6. **Index and asset published separately.** Kilo documents a window where the catalog references a missing archive. Build the index only after the referenced assets exist (or point at immutable commits that already exist).
7. **A review backlog with no automated gate beyond schema checks.** 183 open PRs against 418 commits; the review policy leans on AI sub-agents. Plan automated static checks (manifest schema, pinned ref exists, licence present, no network calls at import) and say plainly what review does and does not cover.

## Hypotheses

- **H1 (out-of-process plugins over the local API are lowest-risk): supports.** Kilo's MCP servers are separate processes or remote services gated per tool; its in-process plugins are the type the docs warn about hardest ("full permissions") and they can hook `permission.ask`. Evidence: marketplace docs "MCP security and permissions" / "Plugin security"; plugins docs hooks table; SECURITY.md.
- **H3 (static Git registry, PR-submitted metadata, CI-built index, pinned developer refs, no backend): partly supports.** Confirmed: one metadata file per item, PR-only, CI generators, generated YAML committed, GitHub Releases for assets, no database. Deviations: the index is served by a Vercel pass-through endpoint with a 1 h cache rather than raw Git (api.ts `DEFAULT_BASE_URL`); skills are copied into the registry and served from a *mutable* `skills-latest` asset, so the "pinned tag/commit" half holds only for git plugins and only when the ref is a 40-hex SHA (git-source.ts `isImmutableRef`); the registry pins upstream `metadata.source.commit` but the client never sees it. Cost is near zero apart from review time (183 open PRs).
- **H4 (hand review does not scale): consistent (inferred).** 183 open PRs vs 418 commits on 2026-10-06; REVIEW.md formalises AI sub-agent review and says CI alone proves nothing about security. PR ages were not checked (API blocked).
- **H5 (declared ≠ enforced): supports with nuance.** Agent `permission` and MCP `{server}_{tool}` rules *are* evaluated by the runtime at call time (host-enforced gate, like Zed), but Kilo states they are not isolation; plugins have no permission model at all and run with the app's own access (like VS Code/Obsidian). So: tool-call gating enforced; process-level containment absent; plugin declarations non-existent.
- **H6 (dependency handling): consistent.** Kilo blocks npm lifecycle scripts, refuses to install dependencies for git plugins (vendor them), shares one Bun cache with dedupe on package+version, and leaves MCP isolation to npx/uvx/docker. No eval/obfuscation policy stated beyond REVIEW.md's "Archives and binaries are inspected rather than treated as opaque."
- **H8 (namespaced ids + declared capabilities with typed I/O): partly supports.** Plugins get collision-free identities (`npm name` or `git/<host>/<owner>/<repo>`); skills/MCPs/agents use a flat kebab-case id with duplicate detection only; `requirements` is typed but not expanded. Shows the cost of a flat namespace, not a working multi-implementation model.
- **H10 (counts need telemetry; stars/dates can come from GitHub at build time; opt-in): consistent.** The catalog carries no counts, stars or dates; the client fetch code logs locally and sends no usage events (api.ts; not an exhaustive audit). Kilo chose to show nothing rather than collect telemetry.
- H2, H7, H9: Kilo does not speak to them.
