# Security of third-party code — research notes (Track E)

- Track: E (security of third-party code, cutting across Tracks A–C)
- Tier: 1
- Date read: 2026-10-06 (every URL below was read on this date unless stated; "not confirmed" marks what could not be verified)
- Brief's question: what can an installed extension do to the user's machine, what actually stops it, what went wrong elsewhere, and what Clips Kitty's plugin manager and registry must do about it.
- Verdict (two lines): In every platform studied, an installed extension runs with the user's full privileges unless the host puts it in a separate process *and* applies an OS or wasm confinement; "declared permissions", "verified" badges and marketplace validation stopped none of the 2024–2026 incidents, which all arrived through install-time code (pip/npm lifecycle scripts, custom wheels, compromised publisher tokens) or pickle model files.
Clips Kitty should treat install as "fetch a pinned commit, verify, no code runs", run plugins out of process under a Job Object (plus restricted token/AppContainer where feasible), give each plugin its own scoped API credential, and reserve "Verified" for a process it can describe.

Structure per case: (a) what an installed extension can do, (b) what stops it, and whether that is enforced or only declared, (c) what happened when something went wrong, (d) lesson for Clips Kitty.

## Case 1 — ComfyUI custom nodes (Ultralytics miner, LLMVISION, January 2025 policy)

### (a) What an installed custom node can do

- A custom node is a Python package imported by the ComfyUI process (see the sibling note `comfyui.md` in this folder for the loader; this note concentrates on the security angle). Nothing between the node and the user's account once it is imported.
- At install, ComfyUI-Manager runs `pip install` for the node's `requirements.txt`. The Manager's own configuration reference lists, among "risk levels for features", "Install via git url, pip install, installation of custom nodes not in default channel" as **High** and "installation of custom nodes in default channel" as **Middle** (https://docs.comfy.org/manager/configuration.md, read 2026-10-06).
- The registry's own description of the threat: nodes "will be scanned for malicious behaviour such as custom pip wheels, arbitrary system calls, etc." (https://docs.comfy.org/registry/overview, read 2026-10-06).

### (b) What stops it

| Control | Where stated | Enforced or declared? |
|---|---|---|
| Registry standards: "The use of `eval` and `exec` functions is prohibited in custom nodes due to security concerns." "Runtime package installation through subprocess calls is not permitted." "Code obfuscation is prohibited in custom nodes." | https://docs.comfy.org/registry/standards (read 2026-10-06) | Declared as policy; the page says only "We will start working with custom nodes that violate these standards to be rewritten." Detection is by registry scanning (below), not by the runtime. |
| Registry scanning and "verification flag": "All nodes will be scanned for malicious behaviour such as custom pip wheels, arbitrary system calls, etc. Nodes that pass these checks will have a verification flag ... beside their name on the UI-manager." | https://docs.comfy.org/registry/overview (read 2026-10-06) | Enforced at publish time by the registry (static). Not a runtime control. |
| January 2025 security update: eval/exec "warning messages now, blocking new additions in 1 month, blocking all public nodes in 3 months"; runtime pip install: "block the incremental addition of pip installation for the registry at runtime" immediately, "full ban on all published nodes in 6 months"; obfuscation: warnings, then "blocking verified nodes that obfuscate code"; detection by "AI and static analysis tools to scan"; a public Discord `#security-review-council` channel. | https://blog.comfy.org/p/comfyui-2025-jan-security-update (dated January 3, 2025; read 2026-10-06) | Enforced at the registry (publication) layer on the timeline stated. The post names "ComfyUI_LLMVISION and ultralytics" as the two prior incidents. |
| Manager `security_level` = `strong` / `normal` / `normal-` / `weak`. `strong`: "Doesn't allow high and middle level risky features"; `normal`: "Doesn't allow high level risky features; middle level features available"; `normal-`: same as normal "if `--listen` is specified and not starts with `127.`"; `weak`: "All features available". | https://docs.comfy.org/manager/configuration.md (read 2026-10-06) | Enforced by the Manager server for the install/update surfaces it owns. Default is `normal`: the Manager source sets `'security_level': default_conf.get('security_level', 'normal')` and a fallback dict `'security_level': 'normal'` (https://raw.githubusercontent.com/Comfy-Org/ComfyUI-Manager/main/glob/manager_core.py lines 1939 and 1971, read 2026-10-06). |
| Newer Manager README (main branch): "Install via git url, pip install, and installation of custom nodes not registered in the default channel are **no longer governed by `security_level`**" but by `allow_git_url_install` and `allow_pip_install`, which "default to `false`", are "Loopback only" ("On a non-loopback listener these surfaces stay denied regardless of the flags"), and the remaining `high` item is "Downloading models that are not in `.safetensors` format and not registered in the default channel model list". Registry-flagged versions ("Flagged CNR versions") "require either all `--listen` addresses to be loopback ... or the explicit override" `allow_flagged_nodepack_install` (default `false`). | https://raw.githubusercontent.com/Comfy-Org/ComfyUI-Manager/main/README.md (read 2026-10-06) | Enforced by the Manager server. Note the docs.comfy.org configuration page still shows the older table (git-url/pip under High); the README is newer. |
| Pinning after an incident: Manager "Automatically pinned ultralytics version to 8.3.40". | https://blog.comfy.org/p/comfyui-statement-on-the-ultralytics-crypto-miner-situation (read 2026-10-06) | Enforced by Manager for that one package. |

What none of this does: once a node is installed and ComfyUI starts, the node's Python runs in the ComfyUI process with the user's privileges. The Manager governs *install surfaces*; the standards govern *what the registry will accept*; nothing confines the code at runtime. The Ultralytics statement says sandboxing is planned (read 2026-10-06; wording in the post is a plan, not a shipped feature).

### (c) What happened

**Ultralytics PyPI compromise, December 2024.**
- ComfyUI statement (dated December 5, 2024; https://blog.comfy.org/p/comfyui-statement-on-the-ultralytics-crypto-miner-situation, read 2026-10-06): versions "v8.3.41 and v8.3.42 of the ultralytics pip package" were compromised; ultralytics is "not a core ComfyUI dependency but it is a dependency of some very popular custom nodes like the ComfyUI-Impact-Pack"; "The compromised ultralytics downloads a binary (crypto miner) on Mac and Linux to /tmp/ultralytics_runner and executes it"; Windows was not affected; "simply doing an update of custom nodes usually does not update the dependencies", so the exposed users were those who installed such nodes (and so ran `pip install -r requirements.txt`) during the window. Response: Manager updated to flag the compromised versions, ultralytics pinned to 8.3.40, desktop app updated; users told to kill the process, delete the file, remove the versions, check with `pip show ultralytics`.
- Primary upstream source: ultralytics issue #18027, "Discrepancy between what's in GitHub and what's been published to PyPI for v8.3.41", opened by `metrizable` on December 5, 2024: "Code in the published wheel 8.3.41 is not what's in GitHub and appears to invoke mining. Users of ultralytics who install 8.3.41 will unknowingly execute an xmrig miner." (https://github.com/ultralytics/ultralytics/issues/18027, read 2026-10-06; the maintainers' replies in that thread were not readable with the tools available here — not confirmed). The v8.3.43 release notes say only "PyPI Security Fix: Ensures secure publication workflow for the Ultralytics package." (https://github.com/ultralytics/ultralytics/releases/tag/v8.3.43, read 2026-10-06). No GitHub Security Advisory for the package could be retrieved (the API path was not reachable from this session) — not confirmed.
- Root-cause narrative, **press/vendor research, not primary**: Wiz reports the attacker's pull requests used a crafted branch name to inject commands through an unsanitized `github.head_ref` in the "Publish Docs" GitHub Actions workflow, leading to a poisoned release; the payload was XMRig (https://www.wiz.io/blog/ultralytics-ai-library-hacked-via-github-for-cryptomining, read 2026-10-06). ReversingLabs reports that 8.3.42 still carried the code, 8.3.43 was clean, and 8.3.45/8.3.46 were later published with the downloader again, "likely" via a stolen PyPI API token (https://www.reversinglabs.com/blog/compromised-ultralytics-pypi-package-delivers-crypto-coinminer, read 2026-10-06 via search summary; the page itself was not opened — not confirmed beyond the summary).
- Install path that carried it: the node's `requirements.txt` → `pip install` at node install time, pulling whatever PyPI served at that moment. No node author did anything wrong; the dependency was poisoned upstream.

**ComfyUI_LLMVISION, June 2024.** The ComfyUI blog names it as one of two prior incidents (https://blog.comfy.org/p/comfyui-2025-jan-security-update, read 2026-10-06). Details are **press only**: Gigazine (dated June 11, 2024; https://gigazine.net/gsc_news/en/20240611-comfyui-llmvision-malware, read 2026-10-06) reports the node by `AppleBotzz` listed custom wheels for the OpenAI and Anthropic libraries in its `requirements.txt`, that those wheels carried a keylogger/stealer which sent browser passwords, credit-card data and history "to a Discord server via webhook", and that it was discovered by Reddit user Rob Laughter in a post titled "PSA: If you've used the ComfyUI_LLMVISION node from u/AppleBotzz, you've been hacked". 404 Media (dated June 11, 2024; https://www.404media.co/hackers-target-ai-users-with-malicious-stable-diffusion-tool-on-github/, read 2026-10-06, paywalled beyond the lead) adds that the archived repository page said "COMPROMISED BY NULLBULGE GROUP". The Reddit post itself could not be loaded (old.reddit.com is blocked from this session) — not confirmed first-hand.
- Install path that carried it: again `requirements.txt`, this time pointing at attacker-controlled wheel files rather than PyPI — exactly the "custom pip wheels" the registry now scans for.

### (d) Lesson for Clips Kitty

1. Both incidents entered through `pip install -r requirements.txt` at install time, one via a poisoned PyPI release, one via a wheel URL in the file. An install step that resolves dependencies live from the network, at the moment the user clicks Install, is the attack surface. Clips Kitty's installer should install from a registry-generated, hash-pinned lockfile (`--require-hashes`, `--only-binary :all:`, see Case 5) and refuse any requirement that is a URL, a path or an unhashed name.
2. ComfyUI needed a flag list ("Flagged CNR versions") and a package pin to respond. Clips Kitty's registry should carry a `flagged`/`revoked` state per version from day one, and the plugin manager should fetch it and refuse to install or enable flagged versions, as Manager now does.
3. Registry standards (no eval/exec, no runtime pip, no obfuscation) are cheap to adopt at launch and expensive to retrofit with a 1-/3-/6-month grace timeline. Adopt them before the first plugin is published.
4. "Updating the node does not update the dependencies" cuts both ways: it limited the Ultralytics blast radius. Clips Kitty should make dependency changes explicit in the lockfile diff shown at update time.

## Case 2 — Kilo Code marketplace: MCP servers and plugins

### (a) What an installed item can do

- The marketplace offers four item types: Agents, Skills, MCP servers and Plugins, installed to project scope (`.kilo/`, shareable through version control) or global scope (https://kilo.ai/docs/customize/marketplace, read 2026-10-06).
- MCP servers: "A local MCP server runs a command as a child process on your machine." (same page). Configuration is a `command` array plus optional `environment` (https://kilo.ai/docs/automate/mcp/using-in-kilo-code, read 2026-10-06). The process runs with the user's privileges; nothing on either page describes a sandbox.
- Plugins: "Plugins run code with full permissions. A plugin can read and change your files, run commands, and access your credentials and network." (marketplace page). A plugin is "a TypeScript or JavaScript module" that "exports a function returning a set of hooks", "loaded at startup", resolved as npm packages via Bun, and its context includes "Bun's shell API" (https://kilo.ai/docs/automate/extending/plugins, read 2026-10-06). Whether plugins run in the Kilo process is not stated; the hook/context design implies in-process (inferred).

### (b) What stops it

| Control | Where stated | Enforced or declared? |
|---|---|---|
| Tool-call permissions: "Control which MCP tools auto-approve, prompt, or are blocked entirely using the same `allow` / `ask` / `deny` permission system as built-in tools." | https://kilo.ai/docs/automate/mcp/overview (read 2026-10-06) | Enforced by Kilo — but on the *agent's tool invocations*, not on the server process. The server is already running as a child process with the user's rights before any prompt appears. |
| "Approve Always": "Click **Approve Always** to save an allow rule to your config so future calls to that tool are auto-approved." Config form `"permission": { "my_server_do_something": "allow" }`. | https://kilo.ai/docs/automate/mcp/using-in-kilo-code (read 2026-10-06) | Enforced; user-weakened with one click. |
| Agent permissions `allow`/`ask`/`deny` for `read`, `edit`, `write`, `bash`, `task`, with wildcards such as `"git *"`, `"src/*"`, `"*.env"`; broad read approvals "do not bypass the built-in prompt for" sensitive files such as `.env`. | https://kilo.ai/docs/customize/agent-permissions (read 2026-10-06) | Enforced for tool calls the agent makes. |
| Marketplace validation: "Marketplace validation is not a security review." Users are told to verify author, source, prerequisites and tools before installing; "Install only plugins that you trust, and review the plugin source and its dependencies." | https://kilo.ai/docs/customize/marketplace (read 2026-10-06) | Declared. No runtime control for plugins. |
| `KILO_PURE=1` disables external plugins (for "reproducible CI runs or debugging"). | https://kilo.ai/docs/automate/extending/plugins (read 2026-10-06) | Enforced on/off switch; not a permission. |
| Credentials: "Keep credentials out of version control", use environment-variable references in project config. | marketplace page | Declared. |

Reading: Kilo's permission system is a good *consent* layer for what the LLM may do, and the vendor is honest that plugins have "full permissions". But the permission prompt is not a boundary around third-party code: the MCP server binary and the plugin module run unconfined.

### (c) What happened

No Kilo-specific incident was found in a search on 2026-10-06 — not confirmed either way. The nearest precedent for the model (extensions published to a marketplace by token-holding developers, run with the editor's privileges) is the Open VSX token leak of October 2025 (Case 5) and the VS Code statement that "The extension host has the same permissions as VS Code itself." (https://code.visualstudio.com/docs/configure/extensions/extension-runtime-security, read 2026-10-06). For the MCP-server half of the model, **vendor research found by search and not opened (not confirmed)**: Koi Security's report of a backdoored `postmark-mcp` npm package (version 1.0.16, September 2025) that BCC'd users' emails to the attacker, and JFrog's report of three malicious MCP servers on PyPI carrying reverse shells (https://research.jfrog.com/post/3-malicious-mcps-pypi-reverse-shell/, October 2025). Both are ordinary package-registry malware; the MCP "server" is simply a process the client spawns with the user's rights.

### (d) Lesson for Clips Kitty

1. Copy the honesty: a plugin listing must say, in the install dialog, exactly what Kilo says — this code can read and change your files, run commands and reach the network — unless the runtime actually confines it.
2. Do not present a consent prompt as a permission boundary. A prompt before the engine *calls* a plugin is fine for UX; the security claim must rest on what the OS enforces around the plugin process (Case 6).
3. "Validation is not a security review" is the right label for CI schema checks. Use that wording in the registry.
4. Separate "allowed to run" (install/enable) from "allowed to do X" (scoped API credential, Case 6/H1): Kilo's `allow/ask/deny` per tool name is a usable model for per-capability scopes on Clips Kitty's local API.

## Case 3 — Open WebUI Functions, Tools, Pipelines: arbitrary Python by design

### (a) What an installed item can do

- Vendor statement: "Tools, Functions, Pipes, Filters, and Pipelines execute arbitrary Python code on your server. This is by design: it's what makes them powerful." (https://docs.openwebui.com/features/extensibility/plugin, read 2026-10-06). The code runs inside the server process (sibling note `open-webui.md` documents `pip install` of frontmatter `requirements` followed by `exec(content, ...)` from source; this note does not repeat it).
- Consequence spelled out by the vendor: malicious code could "exfiltrate data, install malware, mine cryptocurrency, or compromise the instance" (same page, paraphrased from the warning box; read 2026-10-06).

### (b) What stops it

| Control | Where stated | Enforced or declared? |
|---|---|---|
| Who may save code: Functions are admin-only; Tools need the `workspace.tools` permission, "disabled by default for non-admin users" and to be granted only to users trusted like administrators. | https://docs.openwebui.com/security/security-policy (read 2026-10-06); https://docs.openwebui.com/security/vendor-dispositions/cve-2026-0766.txt (read 2026-10-06): "Granting `workspace.tools` is documented as equivalent to giving the user shell access to the server." | Enforced (role/permission check on the routes). It is an *identity* gate, not a confinement. |
| Warnings: "Only install from trusted sources. Never import Tools or Functions from unknown or untrusted sources. Malicious code can compromise your entire system." "Featured does not mean vetted... Listings are community-submitted and unaudited." "Review code before importing." | https://docs.openwebui.com/features/extensibility/plugin (read 2026-10-06) | Declared. |
| Security policy Rule 10: "Open WebUI's Tools and Functions feature is **designed** to execute user-provided Python code on the server. This is core, intentional functionality, not a vulnerability." and "reports describing ANY attack chain that involves Tools or Functions, including but not limited to code execution, file access, network requests, or environment variable access, will be closed as not a vulnerability / intended behavior." Rule 9: "Vulnerabilities that require an administrator to actively perform unsafe actions are not considered valid vulnerabilities." | https://docs.openwebui.com/security/security-policy (read 2026-10-06) | Policy. It defines the extension system as outside the security boundary. |

### (c) What happened

- **CVE-2026-0766 (ZDI-26-032)**: published 2026-01-23 by ZDI, claimed CVSS 8.8, alleging that `load_tool_module_by_id` in `backend/open_webui/utils/plugin.py` lets "a low-privileged authenticated remote attacker ... execute arbitrary Python code" by submitting a Tool that is passed to `exec()`. Vendor disposition: "Rejected, not a vulnerability"; "The record describes a user with permission to run code on the server running code on the server."; the routes "are gated by `user.role == 'admin'` or by the `workspace.tools` permission, which is **disabled by default**"; PR:L in the vector is called inaccurate (should be PR:H). After disputes from 2026-05-04 onward, "ZDI sets the record to REJECTED" on 2026-09-02, "recording the extension system being intended functionality as the reason". (https://docs.openwebui.com/security/vendor-dispositions/cve-2026-0766.txt, read 2026-10-06.)
- **Other advisories**: the repository lists 17 pages of published advisories (https://github.com/open-webui/open-webui/security/advisories, read 2026-10-06). Filtering the list by "tool", "function" and "pipeline" (same URL with `?state=published&query=...`, read 2026-10-06) surfaced no advisory treating Function/Tool/Pipeline code execution as a vulnerability — consistent with Rule 10. Advisories that do touch the extension surface are about *information flow around* it: "Tool source code disclosed to read-only users via the tool list and get endpoints" (GHSA-3r7g-q6cg-q2vx, Moderate, Aug 2, 2026), "Tool source code disclosed to read-only users via the tool export endpoint" (GHSA-2h26-836q-4jh2, Moderate, Sep 27, 2026), "A user's session cookies are sent to tool servers configured for bearer authentication" (GHSA-p78m-89r6-pgf7, Moderate, Sep 4, 2026), "Other users' session tokens disclosed via OAuth-mode connections, tool servers and terminals" (GHSA-gqfh-jxvw-74rp, Moderate, Sep 27, 2026), and the community-site import bridge: "Any website can steal a signed-in user's session token via the community stats message handler" (GHSA-vpq8-f445-hcq7, High, Sep 27, 2026).

### (d) Lesson for Clips Kitty

1. If plugin code runs in the engine process, the only honest security policy is Open WebUI's: declare the whole extension system out of scope and gate it on identity. Clips Kitty has no multi-user identity (local API, no auth), so that gate does not even exist; the plugin must therefore run out of process with real confinement, or the product must say "a plugin is a program you chose to run".
2. The advisories show where the trouble actually lands when execution is "by design": source disclosure, token leakage to third-party tool servers, and a `postMessage` bridge between a community website and the local app. Clips Kitty's registry→app install hand-off must not be a browser bridge from a public website into `127.0.0.1:8765`; use a signed, user-initiated download of a manifest, never a page that can talk to the local API.
3. Keep the vendor's wording: "Featured does not mean vetted" and "Listings are community-submitted and unaudited" are exactly the labels for an unreviewed registry entry.

## Case 4 — Pinokio scripts: "run anything", "isolated by design", "verified"

### (a) What a script can do

- "Scripts can run anything: Just like terminal apps can run shell scripts, Pinokio scripts can run any command, download files, and execute them. Essentially, Pinokio is a user-friendly terminal with a UI." (https://github.com/pinokiocomputer/pinokio README, read 2026-10-06.)
- Docs: "Pinokio script is a declarative markup that can shell commands, work with files, make network requests, and pretty much everything you need to automatically install and run ANYTHING on a computer." and the feature list item "Run any command to automate things on your machine" (https://docs.pinokio.computer, read 2026-10-06 from the documentation copy in the scratchpad `pinokio-docs/README.md` and `program-README.md`).
- Scripts come "from public git repositories"; the install screen shows "an alert letting you know the downloaded 3rd party script is about to be run, as well as the URL to the original script repository" (README).

### (b) What stops it — resolving "run isolated by default" vs "execute anything"

Both statements are true and describe different things:

- "Isolated" means a **file-system layout convention**, not an OS sandbox. README: "By default all Pinokio scripts are stored run under an isolated location (at `~/pinokio/api`). Additionally, all binaries installed through the built-in package managers in Pinokio are installed within `~/pinokio/bin`. Basically, everything you do is stored inside `~/pinokio`. The risk factor is when a script intentionally tries to deviatte away from this. The script verification process checks to make sure this doesn't happen." Docs: `shell.run` activates "the Pinokio-sandboxed `base` environment" (Pinokio's own conda base under `PINOKIO_HOME/bin/miniforge`), a `venv` attribute creates/activates a per-app virtualenv, and "Pinokio does NOT rely on your system-wide setup" (scratchpad `pinokio-docs/README.md` lines 2425, 3682–3686, 8567–8572, read 2026-10-06).
- Nothing in the README or docs describes a restricted token, container, or permission check at runtime. A `shell.run` is a shell command executed with the user's privileges; a `path` outside `~/pinokio` or a global install is merely "out of the ordinary" and is what the human review looks for. So: **isolation is declared and reviewed, not enforced** (inferred from the absence of any enforcement mechanism in the sources read).
- "Verified" means a named, human process. README "Verified Scripts": (1) "Publisher Verification: You must be personally verified to submit scripts for consideration. Contact the Pinokio admin"; (2) invitation to "the official Pinokio Factory GitHub organization as a contributor. Only members of this organization can publish scripts eligible for the 'Discover' page"; (3) "Repository Transfer and Freeze ... you must transfer your script repository to the Pinokio Factory GitHub organization"; (4) once transferred the repo "is considered 'frozen'"; (5) "Review: The script will be thoroughly reviewed and tested by the Pinokio admin."; (6) the admin may "Delist the script" or "Modify the script to resolve the issue. Since the script is under the Pinokio Factory organization, the admin has the rights to make necessary fixes." Checks listed: "Path check", "Venv check", "3rd Party Package check", plus "Checking the reputation of the repository and the developer", "Trhing out the app personally", and confirming the script follows the upstream README; "No scripts are approved until rigorously tested." The Discover page's scripts "are guaranteed to be secure and safe to install" (README, read 2026-10-06).
- Un-verified scripts: any public git URL can be installed; the only control is the alert with the repo URL.

### (c) What happened

No Pinokio incident with a primary source was found in a search on 2026-10-06 — not confirmed. (An automated ANY.RUN sandbox report on the Pinokio 3.6.0 Windows installer flags a PowerShell execution-policy change and a hidden PowerShell window; the service itself states it does not guarantee maliciousness or safety, and this is installer behaviour, not a script incident — not confirmed, not opened.) The design is the same as the one that failed at ComfyUI (Case 1): the verified `wan` script, for example, runs `uv pip install -r requirements.txt` inside a venv (README example), which is isolation from *other apps' dependencies*, not from a poisoned PyPI release.

### (d) Lesson for Clips Kitty

1. Pinokio is the clearest statement of what "Verified" can honestly mean on a $0 budget: identity-checked publisher, repository transferred to an organisation the project controls (so the code cannot change under the badge), one reviewer, a written checklist, and a delist/patch right. Clips Kitty can adopt the same shape (pinned commit under the registry's control instead of repo transfer; see Case 5) and must not claim "guaranteed secure".
2. Say "isolated" only for what the runtime does. A per-plugin venv and a private install root are good hygiene and should be called "installed in its own environment", not "sandboxed".
3. The install-time alert showing the source repository URL is cheap and worth copying, together with the commit hash and the lockfile diff.

## Case 5 — Git-based installation in general

### (a) What `git clone` + `pip install -r requirements.txt` / `npm install` exposes

- **npm lifecycle scripts.** On `npm install` the scripts `preinstall`, `install`, `postinstall`, `prepublish`, `preprepare`, `prepare`, `postprepare` run in that order (https://docs.npmjs.com/cli/v10/using-npm/scripts, read 2026-10-06). They run for dependencies too: `--foreground-scripts` is described as "Run all build scripts (ie, `preinstall`, `install`, and `postinstall`) scripts for installed packages in the foreground process" and `--ignore-scripts` as "If true, npm does not run scripts specified in package.json files." (https://docs.npmjs.com/cli/v10/commands/npm-install, read 2026-10-06). The scripts guide's best-practice list includes not prefixing commands with `sudo` and not using scripts for things users would not expect.
- **Python source distributions.** For sdists and local directories "pip determines project metadata using the project's build backend" — i.e. the package's own build code runs at install (https://pip.pypa.io/en/stable/cli/pip_install/, read 2026-10-06). `--only-binary` "Do not use source packages ... ':all:' to disable all source packages"; `--no-deps` "Don't install package dependencies." pip's secure-installs page warns against `python setup.py install` / `easy_install` because they "download unchecked dependencies" (https://pip.pypa.io/en/stable/topics/secure-installs/, read 2026-10-06).
- **`.pth` files.** Any installed package can drop a `.pth` file into site-packages; "Lines starting with `import` (followed by space or tab) are executed." and "An executable line in a `.pth` file is run at every Python startup, regardless of whether a particular module is actually going to be used." (https://docs.python.org/3/library/site.html, read 2026-10-06). This is code that runs on every interpreter start without any import by the plugin.
- **Hash-checking mode** (the defence): activated by `--require-hashes` or by any `--hash=` in the requirements file; "Hashes are required for *all* requirements"; "Hashes are required for *all* dependencies"; "Requirements must be pinned (either to a URL, filesystem path or using `==`)"; SHA256 recommended, MD5/SHA1 excluded; `--no-require-hashes` (pip 26.2) relaxes it for local/VCS entries (https://pip.pypa.io/en/stable/topics/secure-installs/, read 2026-10-06).
- **Mutable refs.** pip accepts `git+https://...@master`, `@v1.0` and `@da39a3ee...` and says "specifying a full hash is preferable to a partial hash" (https://pip.pypa.io/en/stable/topics/vcs-support/, read 2026-10-06). Git's own documentation on re-tagging: `-f` will "Replace an existing tag with the given name"; "If somebody got a release tag from you, you cannot just change the tag for them by updating your own one. This is a big security issue, in that people MUST be able to trust their tag-names." (https://git-scm.com/docs/git-tag, read 2026-10-06). Branches move by design. Only a commit hash identifies content.
- **GitHub immutable releases** (opt-in): "Immutable releases are releases where the assets and associated Git tag cannot be changed after publication."; the tag "cannot be changed, and cannot be deleted while the release exists"; "Creating an immutable release automatically generates a release attestation, which is a cryptographically verifiable record of a release containing the release tag, commit SHA, and release assets." (https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases, read 2026-10-06). GitHub's changelog entry "Immutable releases are now generally available" is dated 2025-10-28 by its URL (https://github.blog/changelog/2025-10-28-immutable-releases-are-now-generally-available/, found by search 2026-10-06; page not opened — not confirmed beyond the title).
- **Typosquatting.** PyPI primary sources on the March 2024 flood could not be located (not confirmed); press (Checkmarx, https://checkmarx.com/blog/pypi-is-under-attack-project-creation-and-user-registration-suspended/, found by search 2026-10-06, not opened) reports 500+ typosquatted packages with malicious `setup.py` and a roughly ten-hour suspension of new registrations on 2024-03-28 — **press, not confirmed**. PyPI's own "Project Quarantine" post (dated 2024-12-30 by its URL; https://blog.pypi.org/posts/2024-12-30-quarantine/, read 2026-10-06) says a quarantined "Project is not installable (hidden from simple index) while in quarantine", that administrators quarantine projects, and that about 140 projects were quarantined since August 2024 with one released.

| `--only-binary :all:` + `--require-hashes` + `==` pins | pip, if the lockfile is complete | pip docs above |

### (c) What happened

- **npm "Shai-Hulud" worm, September 2025.** CISA alert dated September 23, 2025 (https://www.cisa.gov/news-events/alerts/2025/09/23/widespread-supply-chain-compromise-impacting-npm-ecosystem, read 2026-10-06): "over 500 packages" compromised; the actor, after compromising developer accounts, "leveraged an automated process to rapidly spread by authenticating to the npm registry as the compromised developer, injecting code into other packages, and publishing compromised versions to the registry"; the payload harvested GitHub PATs and AWS/GCP/Azure keys, "Exfiltrated the harvested credentials to an endpoint controlled by the actor" and to a public repository named `Shai-Hulud`. Mitigations: "Pin npm package dependency versions to known safe releases produced prior to Sept. 16, 2025", review lockfiles, "Immediately rotate all developer credentials", "Mandate phishing-resistant multifactor authentication (MFA) on all developer accounts", block `webhook.site`. GitHub's own post (dated September 22, 2025; https://github.blog/security/supply-chain-security/our-plan-for-a-more-secure-npm-supply-chain/, read 2026-10-06) describes the vector as "compromised maintainer accounts by injecting malicious post-install scripts into popular JavaScript packages", says GitHub removed "500+ compromised packages", and announces: trusted publishing, "deprecate legacy classic tokens", granular tokens with a "limited lifetime of seven days", "require 2FA for any writes and publishing actions", "remove the option to bypass 2FA for local package publishing", "set publishing access to disallow tokens by default", and migration from TOTP to FIDO 2FA.
- **Open VSX leaked tokens, October 2025.** Eclipse Foundation blog (status update dated October 21, 2025; https://blogs.eclipse.org/post/mikaël-barbero/open-vsx-security-update-october-2025, read 2026-10-06): developers "inadvertently exposed" publishing tokens in public repositories; "a small number of tokens had been leaked and could potentially be abused to publish or modify extensions"; attackers used some to publish malicious extensions (the campaign Koi Security called "GlassWorm", which Open VSX says was not self-replicating and aimed to "steal developer credentials"); the reported 35,800 downloads figure "overstates the actual number of affected users, as it includes inflated downloads generated by bots"; tokens "revoked immediately once identified", "All known malicious extensions were removed from Open VSX immediately upon notification"; a token prefix format was introduced with Microsoft's MSRC for secret scanning; planned: shorter default token validity, faster revocation, and "Automated scanning of extensions will now occur at the time of publication".
- **PyPI LiteLLM/Telnyx, March 2026.** PyPI incident report (dated 2026-04-02 by URL; https://blog.pypi.org/posts/2026-04-02-incident-report-litellm-telnyx-supply-chain-attack/, read 2026-10-06): "After an API token exposure from an exploited Trivy dependency releases of the packages litellm and telnyx were published to PyPI containing credential harvesting malware." "The malware ran on install, harvesting sensitive credentials and files, and exfiltrating to a remote API." Exposure windows: litellm 2 h 32 min, telnyx 3 h 42 min from upload to quarantine; roughly 119,000 litellm downloads in the window; 13 malware reports; telnyx was quarantined automatically through a trusted-reporter pool. Guidance: dependency cooldowns (`uv` or pip v26.1+, e.g. "P3D"), "If you're a developer of an application using PyPI packages you should be using lock files both for security and reproducibility", trusted publishers over API tokens, phishing-resistant 2FA. Which install hook executed the payload is not stated on that page — not confirmed.
- **Hugging Face pickle models.** HF's pickle page (https://huggingface.co/docs/hub/security-pickle, read 2026-10-06): "pickle is dangerous because: when importing a python module, arbitrary code can be executed; you can import builtin functions like `eval` or `exec`...; when instantiating an object, the constructor may be called"; the Hub runs ClamAV plus a "Pickle Import scan" via `pickletools.genops` on every uploaded pickle and shows the imports; "***Disclaimer***: this is not 100% foolproof. It is your responsibility as a user to check if something is safe or not."; recommendation: trusted sources, signed commits, TF/Flax weights, or safetensors. Malware scanning: "every file of your repositories that is smaller than 2 GB" is run through ClamAV at each commit (https://huggingface.co/docs/hub/security-malware, read 2026-10-06). Third-party scanner: Protect AI Guardian "catches pickle, Keras, and other exploits" and scans public repositories (https://huggingface.co/docs/hub/security-protectai, read 2026-10-06). Documented malicious-model incident, **vendor research, not HF primary**: ReversingLabs (dated 2025-01-20 report to HF; https://www.reversinglabs.com/blog/rl-identifies-malware-ml-model-hosted-on-hugging-face, read 2026-10-06) found two models (`glockr1/ballr7`, `who-r-u0000/0000000000000000000000000000000000000`) whose PyTorch files were 7z-compressed pickles carrying "a typical platform-aware reverse shell that connects to a hardcoded IP address"; picklescan missed them because validation failed partway while "Pickle deserialization works like an interpreter, interpreting opcodes as they are read"; HF "removed malicious models in less than 24 hours" and updated picklescan for "broken" pickles. No HF-authored incident post was found — not confirmed as a primary source.

### (d) Lesson for Clips Kitty

1. Install must execute nothing: no npm lifecycle scripts (always `--ignore-scripts`), no sdists (`--only-binary :all:`), no `.pth`-dropping packages (reject wheels that contain `.pth` files during registry CI), no VCS or URL requirements.
2. The index must point at a commit hash, and the installer must verify it; a tag is a label, not an identity (git-tag doc). Encourage immutable releases + attestations for "Verified".
3. The registry's CI should build the per-plugin lockfile with hashes from a clean resolver, with a cooldown (reject versions younger than N days unless the publisher signs off), so a poisoned release has to survive N days of public scrutiny before any Clips Kitty user can get it.
4. Every one of the 2025–2026 registry incidents began with a stolen or leaked publisher credential (npm accounts, Open VSX tokens, PyPI token via Trivy). A PR-based Git registry inherits GitHub's 2FA and secret scanning for free; require 2FA-enabled accounts for publishers, and never issue long-lived registry tokens.
5. Models: default to safetensors; a pickle (`.pt`, `.ckpt`, `.bin`) must be pinned to a HF commit, scanned for imports with `pickletools.genops` before load, and shown with a warning. Scanners are "not 100% foolproof" (HF) — say so.

Practical reading for Clips Kitty (inferred from the table): a Job Object costs nothing and should wrap every plugin process (kill-on-close, memory, process count, CPU time). A restricted token costs nothing at runtime but needs engineering (alternate desktop, ACLs for the plugin's working folder). An AppContainer is the only user-mode option that confines network and devices and it is what Chromium uses; it is "complicated" for unpackaged processes and needs ACLs for every path the plugin may read, including model caches. Windows Sandbox, WSL and Docker all require Pro/Enterprise editions or an extra install and are not plugin hosts. Wasm is the only option where a declared capability is a hard boundary, and it only fits logic-only plugins.

## Hypotheses

**H1 — "Out-of-process plugins speaking the local API are the lowest-risk model."** Verdict: **confirmed with two conditions, otherwise rejected.** A child process by itself grants nothing: Kilo's "local MCP server runs a command as a child process on your machine", Pinokio's `shell.run`, and Electron's `utilityProcess` (no sandbox option) all run with the user's full rights, and Clips Kitty's API on `127.0.0.1:8765` has no authentication, so any local process, plugin or not, can already drive it. What process separation *does* buy is (1) the engine's memory and import table stay out of reach (Open WebUI shows the alternative: module top-level code "monkey-patches ... installed in the live application", per the sibling note and the vendor's Under-the-Hood page), and (2) the OS confinement primitives in Case 6 apply per process, which is exactly how Chromium builds its sandbox. So H1 holds if (a) each plugin process is created under a Job Object and, where it does not need GPU/device access, a restricted token or AppContainer, and (b) each plugin gets its own API credential with declared scopes that the engine checks server-side. Without (a) and (b), out-of-process is a stability model, not a security model. For logic-only plugins, wasm with host-checked capabilities (Zed) is strictly lower risk than any native process.

**H5 — "A declared permission is not an enforced one."** Verdict: **confirmed.** VS Code: "The extension host has the same permissions as VS Code itself. This means that any action that VS Code can perform, an extension can also perform through the extension host." (https://code.visualstudio.com/docs/configure/extensions/extension-runtime-security, read 2026-10-06). Obsidian: "Obsidian cannot reliably restrict plugins to specific permissions or access levels. This means that plugins will inherit Obsidian's access levels." and "By default, Obsidian runs in Restricted Mode to prevent third-party code execution." (https://obsidian.md/help/plugin-security, read 2026-10-06). Open WebUI: "execute arbitrary Python code on your server. This is by design". Kilo: "Plugins run code with full permissions"; its allow/ask/deny governs the agent's calls, not the server process. ComfyUI's `security_level` governs install surfaces, not runtime. Pinokio's "isolated by default" is a layout convention checked by a reviewer. The one counter-example is host-enforced: Zed returns an error "when an extension attempts to call the corresponding extension API without sufficient capabilities", because the extension is wasm and can only reach what the host links in. Rule for Clips Kitty: the manifest may *declare* capabilities, but the UI may call a permission "enforced" only for (i) API scopes the engine checks per plugin credential, (ii) OS limits applied to the plugin process, (iii) wasm imports. Everything else is "declared by the developer".

**H6 — dependency handling.** Verdict: **confirmed on both halves.** Policy: ComfyUI's standards say "Runtime package installation through subprocess calls is not permitted.", ban `eval`/`exec` and obfuscation, and the January 3, 2025 update set the phase-out timeline after "ComfyUI_LLMVISION and ultralytics"; the registry scans for "custom pip wheels, arbitrary system calls". Shared environment invites conflicts: ComfyUI-Manager ships `pip_overrides.json`, `pip_blacklist.list`, `pip_auto_fix.list` ("automatically restore specified versions when ... versions get mismatched during custom node installations") and `downgrade_blacklist` (https://docs.comfy.org/manager/configuration.md, read 2026-10-06) — four pieces of machinery that exist only because nodes share one environment; Open WebUI pip-installs every function's `requirements` into the server's own environment with no conflict resolution (sibling note). One environment per plugin costs disk: Pinokio's docs state "ALL of these apps have the same redundant packages installed (`torch`, `accelerate`, `xformers`, etc.)" and add "venv linking"/Disk Saver to deduplicate (scratchpad `pinokio-docs/README.md` lines 5289–5298 and 8574, read 2026-10-06). Recommended shape (inferred): one venv per plugin built from the registry's hash-pinned lockfile, with a shared wheel cache and hard-linked/deduplicated site-packages where the OS allows, and the heavy runtimes (torch, FFmpeg, faster-whisper, YOLO, Ollama) provided by the host over the API rather than re-installed per plugin.
